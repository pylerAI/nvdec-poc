# How we got here: the trial-and-error path to NVDEC decoding in vLLM

One page on what we tried, what broke, and what each failure taught us. Dates are 2026.

| # | Step | What happened | Lesson / fix |
|---|---|---|---|
| 1 | **Baseline: CPU decode** (vLLM 0.20.2, OpenCV/PyAV inside 12 API-server processes) | Worked, but 1080p shots cost 3–36 cpu-s per request and the 16-core pod quota of our live endpoint, not the GPU, set the ceiling. | Decode is a fixed CPU tax per request that scales with resolution × length, not with model size. |
| 2 | **First NVDEC attempt** (vLLM 0.28.0 `pynvvideocodec`) | Backend refused our HLS MPEG-TS segments: PyNvVideoCodec cannot index TS. | Need a TS path of our own. |
| 3 | **Patch v1: whole-segment decode** — fresh `CreateDemuxer`+`CreateDecoder` per request, decode all 180 frames, `from_dlpack` per frame | ~300 ms per 6 s segment in isolation; under 64 concurrent requests p50 **6.4 s vs 1.2 s on CPU**. API servers burned 1.4 cpu-s/request spinning in CUDA sync while the GPU showed 100 % SM. Rolled back. | Decode issued from many CUDA contexts on the inference GPU queues behind inference; per-request decoder creation and full decode are both wrong. |
| 4 | **CUDA MPS was off** | Twelve API-server contexts + engine were time-slicing the GPU. Enabling MPS (`nvidia-cuda-mps-control -d` in the image entrypoint) removed the spin (1.4 → 0.39 cpu-s) but not the latency. | MPS is a prerequisite for multi-process decode on the inference GPU — necessary, not sufficient. Later confirmed in isolation: without MPS multi-process NVDEC caps at ~2,300 frames/s regardless of resolution (§4.1 of the report). |
| 5 | **NVIDIA DevTech consultation (09-12)** | Advice: reuse decoders (decoder caching), decode only the frames you need, TS is a known gap. | Both points are what vLLM's *upstream MP4 path* already does (`SimpleDecoder.get_batch_frames_by_index` + `reconfigure_decoder` slots). Don't rewrite that path — route TS into it. |
| 6 | **Microbenchmarks on an isolated pod** (`bench/nvdec_advice_bench.py`) | Fresh decoder per clip 297 ms vs **33 ms reused** (9×; `CreateDecoder` itself is 1.7 ms — cost is on first frames). TS demuxer `Seek`/`TimestampFromFrame` SIGSEGV; `SetSeekPTS` ignored; `SimpleDecoder(need_scanned_stream_metadata=True)` on TS → IndexError/SIGSEGV. PyAV stream-copy TS → fMP4 costs **5 ms**, and the remuxed stream indexes fine. | Remux is the cheapest correct workaround; all seek-on-TS routes are dead ends in 2.1.1. |
| 7 | **Patch v2: remux-and-fall-through** (`patches/nvdec_mpegts.py`) — two helpers + a two-line guard | 6 s segment: 5 ms remux + **20 ms** decode of 12 sampled frames with reused slots (was ~300 ms). `hw_decoders` 2 vs 4 vs 7: identical — `SimpleDecoder` holds the GIL, so threads in one process don't scale; the 12 processes do. | Smallest diff won. Per-process serialization is a binding limitation to report upstream, not to engineer around. |
| 8 | **Adding VOD** — cut a 43-min 1080p title into 10/30/120 s shots by stream copy | NVDEC path failed with "Decode Error occurred for picture N" + IndexError: cuts landed on non-IDR keyframes (open GOP). FFmpeg tolerated the same files with corrupt leading frames. | Re-encode shots with closed GOPs (`-g 30 -sc_threshold 0`) or cut at IDR frames. Frame-accurate NVDEC indexing needs clean GOP structure. |
| 9 | **Measurement pitfalls** | Same-clip load hit vLLM's prefix/processor caches (optimistic latencies); server CPU had to come from the pod cgroup (`cpu.stat`), not the client; torch spawned 112 threads per process on a 224-core host (`OMP_NUM_THREADS=1`); py-spy/perf blocked in the container; running benches on a node shared with production contaminated both; 120 s shots at 1 fps overflowed a 32k context on an earlier model; multi-process throughput was skewed by process start-up until workers synchronized on a barrier. | Isolated pod, one GPU, fresh server per configuration, warm-up, 3 repetitions, distinct clips for VOD, compare configurations against each other rather than trusting absolute numbers. |
| 10 | **Final matrix on one B200** (`bench/run_all.sh`, Nemotron 3 Nano Omni, vLLM 0.28.0) | Raw: 12,180 frames/s on 2 cores vs 4,760 on 57 cores. Loader: 2.0×/2.0×/5.3× for 10/30/120 s 1080p. E2E: 3–11× less CPU per request, 13–31 % lower p50 for 1080p, parity for 360p 6 s segments. | The gain is first a CPU gain; it becomes a latency gain when decode is a visible share of the request. |

**What we would tell someone starting today**

1. Turn on MPS before anything else if more than one process decodes on the inference GPU.
2. Use vLLM's upstream `pynvvideocodec` path (sampled frames, decoder slots); only add the remux in front of it for MPEG-TS.
3. Feed closed-GOP MP4 (or cut at IDR) — NVDEC indexing is stricter than FFmpeg.
4. Measure CPU per request from the cgroup and on an isolated host; short low-res clips will show CPU savings but no latency win.
5. Report the binding limits upstream rather than working around them: TS indexing, GIL-holding `SimpleDecoder`, open-GOP hard failure (`docs/nvidia-issues.md`).
