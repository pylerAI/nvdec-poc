## 요약

라이브 6초 360p MPEG-TS 세그먼트 1건이 vLLM 0.28.0(B200 1장)을 거치는 1~9단계를 각각 실측했습니다. 먼저 이전 PoC 모델인 Nemotron 3 Nano Omni로 측정하고, 이어서 운영 live-ingest 모델인 Qwen3-Omni-30B-A3B-Instruct를 운영과 동일한 서버 인자·요청 형식으로 다시 측정했습니다. 이전 표의 추정치(전처리 267 cpu-ms, 오디오 300 cpu-ms, 인코더·프리필 "분리 측정 못 함")를 실측값으로 대체하고, 각 병목에 대한 개선 실험을 함께 수행했습니다.

1. **이전 PoC는 API 서버 1개로 동작하고 있었습니다.**
   - vLLM 0.28.0의 `python -m vllm.entrypoints.openai.api_server`는 `--api-server-count`를 무시하고 단일 프로세스로 기동됩니다(`run_server`, "single-worker API server").
   - 12개 모드는 `vllm serve`에서만 동작합니다. `bench/e2e_matrix.sh`가 전자의 방식을 쓰기 때문에 REPORT의 "API 서버 12개" 수치는 실제로는 1개 기준이었습니다.
   - 운영 엔드포인트는 `vllm serve`로 기동되므로 이 문제와 무관합니다.
3. **영상 디코드(3번)가 요청 시간에서 차지하는 비중은 두 모델 모두 작습니다.** (여기서 디코드는 영상 디코드이며, vLLM 용어의 디코드(토큰 생성, 9번)와 다릅니다.)
   - NVDEC(22 ms)
     - Nemotron 1건 4.4%, 64동시 2.1%
     - Qwen 1건 1.2%, 64동시 0.5%.
   - OpenCV(55 ms, 182프레임 전부 디코드)
     - Nemotron 1건 약 11%, 64동시 약 2.7%
     - Qwen 1건 약 2.9%, 64동시 약 0.9%.
   - 이 수치는 6초 360p 라이브 세그먼트 기준이며, 이전 PoC의 1080p VOD에서는 디코드가 요청의 큰 몫(CPU 경로 3.3~36 cpu-s/요청)이었습니다.
4. **그래서 NVDEC의 이득은 두 모델 모두 CPU 절감에 한정됩니다.** 요청의 소요 시간은 줄지 않고 CPU 사용량만 줍니다.
   - 소요 시간
     - 1건 p50은 Nemotron 0.51 vs 0.50 s, Qwen 1.92 vs 1.87 s이고,
     - 64동시 p50은 Nemotron 4.85 vs 4.82 s로 같습니다.
     - Qwen 64동시에서는 NVDEC 쪽이 오히려 약 1초 느립니다(14.6 vs 13.5 s; 원인은 4번).
   - CPU
     - OpenCV 디코드는 요청당 약 150 cpu-ms로 API 서버 CPU(0.40~0.45 cpu-s/요청)의 약 1/3을 차지합니다.
     - NVDEC으로 바꾸면 요청당 API 서버 CPU가 Nemotron 0.45 → 0.20 cpu-s, Qwen 0.40 → 0.16 cpu-s로 절반 이하가 됩니다. 
     - 운영 파드의 CPU limit 16코어 기준으로 5 req/s에서 CPU 디코드는 약 2코어, NVDEC은 약 0.8코어를 씁니다.
   - 따라서 NVDEC 유지 여부는 지연이 아니라 CPU 예산으로 판단하면 됩니다.
     - NVDEC을 사용할 경우 MPS는 필수입니다(MPS 없이는 64동시 디코드가 53 → 973 ms로 급증, API 서버 CPU 0.74 cpu-s/요청). 
     - 1080p VOD처럼 디코드 비중이 큰 입력에서 NVDEC이 지연도 13~31% 줄였던 이전 PoC 결과와는 모순되지 않습니다.
5. **NVDEC은 B200의 연산 자원을 쓰지 않지만, 메모리와 공유 오버헤드는 소폭 늘어납니다.**
   - NVDEC은 SM과 분리된 고정 기능 장치(B200에 7개)로, LLM 추론 중에는 비어 있는 자원입니다.
     - 이번 측정에서 NVDEC 사용률은 버스트 시작 순간에만 20 ~ 24%였고, SM 사용률은 두 구성 모두 30 ~ 40%대로 차이가 없었습니다.
   - 대신 API 서버 12개가 각자 CUDA 컨텍스트와 디코더를 갖습니다.
     - Qwen NVDEC 구성에서 GPU 메모리 사용량이 183 GB 중 182 GB였는데, 엔진 몫(`--gpu-memory-utilization 0.9` = 165 GB)을 제외한 약 17 GB(서버당 약 1.4 GB)가 이 컨텍스트·디코더 몫입니다. CPU 디코드 구성에서는 이 메모리를 쓰지 않습니다. 운영 설정에서는 들어가지만 여유가 약 1 GB뿐입니다.
   - 이 컨텍스트들이 디코드 결과를 GPU→CPU로 복사하고 동기화하면서 엔진과 GPU 스케줄링을 나눠 쓰는 비용이 3번의 "Qwen 64동시 약 1초"입니다. MPS 자체의 오버헤드는 작습니다(CPU 디코드 + MPS ≈ CPU 디코드).
6. **Nemotron: 64동시 요청의 병목은 인코더입니다.** 비디오를 하나씩 순차적으로 인코딩하기 때문에(`requires_sequential_video_encoding`) 64요청 버스트 1회의 wall 5.0초 중 3.1초(62%)가 인코더 호출에 소요됩니다(비전 64회 × 33 ms + 오디오 8회 × 80 ms의 합계). 한 스텝의 영상들을 ViT 한 번의 호출로 묶어 처리하는 실험에서 **p50 4.85 → 3.4 s, 처리량 13.0 → 18.4 req/s**를 얻었고, 출력은 비트 단위까지 동일했습니다.
7. **Qwen3-Omni(운영 형식): 생성 단계가 지배적입니다.** 시스템 프롬프트 약 4,000토큰(프리픽스 캐시 적중) + 비디오 1,320 + 오디오 82토큰을 입력으로 JSON 약 230토큰을 생성하는데, 1건 1.92 s 중 생성이 1.63 s(85%)를 차지합니다. 64동시 p50 14.6 s, 4.2 req/s입니다.
8. **Qwen3-Omni의 병목 두 가지와 해법.** (a) 구조화 출력(xgrammar)이 64동시에서 토큰당 생성 시간을 2배로 늘립니다(적용 시 38 ms, 미적용 시 16~24 ms; 1건에서는 차이 없음). (b) 러너가 인코더 입력을 요청 순서대로 [영상, 오디오, 영상, 오디오, …]로 전달하는데 vLLM은 연속된 동일 모달리티만 묶기 때문에, 오디오+영상 요청에서는 인코더가 항목마다 개별 호출됩니다. 모달리티별 안정 정렬 한 줄을 추가하면(`SORT_MM=1`) **p50 14.6 → 10.5 s, 4.2 → 5.9 req/s**가 됩니다.
9. **1080p에서는 NVDEC이 필수가 되고, Nemotron은 전처리가 1건의 41%를 차지합니다.**
   - 실제 1080p 방송(월드컵 중계)에서 `seg6.ts`의 인코더 특성을 복사해 만든 6초 세그먼트 800개로 같은 하네스를 다시 돌렸습니다(`results/live1080_stages_2026-10-08.md`).
   - CPU(OpenCV) 디코드
     - 1080p 180프레임을 전부 디코드하느라 64동시에서 요청당 API 서버 CPU 3.1~3.2 cpu-s를 씁니다(NVDEC 0.37~0.54).
     - 운영 CPU limit 16코어에서 5 req/s면 15코어라 CPU 디코드로는 운영이 안 됩니다.
     - 지연도 NVDEC이 빠릅니다: Qwen 16.2 vs 18.0 s, Nemotron 5.52 vs 6.47 s (10~15%; 360p에서는 CPU가 같거나 빨랐음).
   - Nemotron 전처리
     - 1080p → 672×384 리사이즈(CPU)가 109 → 353 ms로 3배가 되어 1건 0.88 s의 41%입니다.
     - 64동시에서는 대기 포함 1.0 s입니다.
     - "전처리를 엔진 GPU로"가 Nemotron 1080p에서는 2순위로 올라갑니다. Qwen은 118 ms(1건의 4%)입니다.
   - 인코더 개선은 1080p에서도 유지됩니다.
     - Qwen 정렬: 64동시 16.2 → 12.8 s (−21%)
     - Nemotron 배치 처리: 5.52 → 4.29 s (−22%), 출력 동일
   - Qwen은 여전히 생성이 지배합니다.
     - 1건 2.80 s 중 생성 2.3 s (79%)
     - 내용이 다양해져 출력이 230 → 314토큰으로 길어진 것이 1건 지연 증가(1.92 → 2.80 s)의 2/3입니다.
     - 토큰당 생성 시간은 해상도와 무관합니다.
10. **VOD(14초 장면 클립)도 결론은 같습니다: 생성이 지배하고, 1080p는 NVDEC이 CPU 한도를 지켜 줍니다.** 운영 VOD 경로(`worker-captioning`: `-c copy` 장면 mp4 + 16 kHz WAV `audio_url`, API 서버 3개, OpenCV, MPS 없음)를 재현해 같은 내용의 360p·1080p 클립으로 쟀습니다(`results/vod14s_stages_2026-10-08.md`).
    - 생성(9번)이 1건의 67 ~ 80%, 운영 배치(8동시)의 68 ~ 75%, 64 동시의 63 ~ 68%입니다. 14초 클립은 출력이 320~365토큰입니다.
    - 360p는 디코더를 바꿔도 지연이 같습니다(1건 2.78 vs 2.80 s, 8동시 5.67 vs 5.67 s). CPU만 0.8 → 0.3 cpu-s/요청.
    - 1080p OpenCV 디코드는 요청당 API 서버 CPU 3.55(1건) / 4.75(8동시) / 7.9(64동시) cpu-s로 16코어 한도를 위협합니다. NVDEC은 0.6 cpu-s이고 지연은 8동시 −3%, 64동시 −6%(API 서버 3개) / −13%(12개)입니다.
    - 64동시에서는 API 서버 3개의 전처리 스레드가 병목입니다(대기 포함 1080p 5.8 s, 360p 2.4 s). 12개로 늘리면 1.1 / 0.6 s가 되지만 프리필 대기가 1.0 → 4.1 s로 늘어 p50은 28.0 → 24.3 s에 그칩니다. 운영 배치 8동시에서는 3개로도 대기가 0.4~0.9 s입니다.
    - 1080p는 360p보다 1건 0.6 s(22%) 깁니다: 디코드 +0.22 s, 전처리 +0.33 s. 비디오 토큰 3,080 → 4,186이지만 프리필은 +0.02 s입니다.
    - 결론
      - 360p만 들어온다면 NVDEC은 지연 이득이 없고 CPU만 0.8 → 0.3 cpu-s/요청 줄입니다. CPU 여유가 있으면 바꿀 이유가 없습니다.
      - 1080p 업로드가 섞이면 NVDEC(+MPS)이 필요합니다. OpenCV 디코드의 3.5 ~ 7.9 cpu-s/요청이 파드 16코어 한도를 위협하고, NVDEC은 0.6 cpu-s에 지연도 8동시 −3%, 64동시 −6 ~ 13%입니다.
      - API 서버는 3 → 4~6개면 충분합니다. 운영 배치(8동시)에서는 3개로도 대기가 작고, 12개는 64동시에서만 효과가 있으며 엔진 프리필 대기로 상쇄됩니다.
      - 가장 큰 몫은 여전히 생성이라, 구조화 출력 오버헤드·출력 토큰 수 같은 live의 1순위 조치가 VOD에도 그대로 적용됩니다.

- CPU 사용량 기준으로는 5번 전처리(80~112 cpu-ms)가 가장 큽니다. 동일 함수를 `OMP_NUM_THREADS` 1/2/4/8로 실행하면 88/47/28/18 ms, B200에서는 0.4 ms입니다. 오디오의 프론트엔드 비용은 약 8 cpu-ms입니다.

- 배치(batch) 처리 실험(`BATCH_VIDEO=1`)
  - 모델 클래스에서 `requires_sequential_video_encoding`을 제거하고, 프레임 수가 같은 영상들을 `extract_feature` 한 번의 호출로 처리합니다. RADIO의 비디오 경로는 튜블릿 단위로 블록 대각 마스크 어텐션을 수행하고 위치 인코딩도 공간 축에만 적용되므로, 영상을 묶어도 서로 영향을 주지 않습니다. 영상 5·14·4개를 한 번에 묶은 호출에서 영상별 호출 결과와 비교한 max abs diff는 0.0이었습니다. EVS(`--video-pruning-rate`)를 켜면 러너가 영상을 다시 분리하므로 해당 조건도 함께 수정해야 합니다.
  - CPU(OpenCV) 디코드 + 배치 처리 조합은 측정하지 않았습니다. 배치 처리는 엔진 쪽 변경이라 디코더와 무관하고(64동시에서 CPU 4.82 s ≈ NVDEC 4.85 s), 무엇보다 OpenCV 백엔드는 이 TS 세그먼트에서 프레임 수를 실제보다 크게 추정해 11프레임(홀수)을 내기 때문에 "프레임 수가 같고 T=2의 배수"라는 배치 조건에 걸려 영상별 처리로 되돌아갑니다. 적용하려면 OpenCV 샘플링을 고쳐 12프레임이 나오게 하거나, 영상마다 마지막 프레임을 복제해 짝수로 맞추는 처리가 먼저 필요합니다.

## Qwen3-Omni (운영 모델, 운영 요청 형식)

각 행은 독립 실험이며(누적 아님), 두 가지를 함께 적용한 것은 마지막 행뿐입니다.

- **`response_format` 제거\***: 운영 요청의 `response_format`(json_schema, 필드 15개)은 xgrammar가 토큰을 생성할 때마다 "스키마상 다음에 올 수 있는 토큰"만 남기는 마스크를 씌워 강제합니다(구조화 출력). 이 행은 같은 요청에서 그 항목만 뺀 것으로, 문법 강제 비용을 분리하기 위한 실험입니다. 64동시 토큰당 생성 38 → 16~24 ms, 1건은 변화 없음. 다만 강제가 없으면 영상만 있는 요청의 출력 길이가 4~600토큰으로 불안정해져 처리량 비교는 무의미하므로(—), 토큰당 생성 시간만 비교합니다.
- **`--async-scheduling` 추가**: 기본 동작은 스텝마다 CPU(스케줄링, 샘플링 후처리)와 GPU(forward)가 번갈아 도는데, 이 플래그는 GPU가 현재 스텝을 도는 동안 CPU가 다음 스텝을 준비해 둘을 겹칩니다. 64동시 토큰당 생성 38 → 33 ms(약 9%), 1건은 변화 없음. 구조화 출력과 함께 써도 오류가 없었고, 정렬과 겹쳐 쓰면 추가 효과는 없었습니다.
- **인코더 모달리티 정렬 (`SORT_MM=1`) 추가**: 엔진은 스텝마다 인코딩할 항목을 요청 순서대로 [영상1, 오디오1, 영상2, 오디오2, …]로 모으는데, vLLM은 연속된 같은 모달리티만 묶기 때문에 오디오+영상 요청에서는 항목마다 인코더를 따로 부릅니다. 이 패치는 러너의 `_batch_mm_inputs_from_scheduler`가 반환하는 해시·kwargs·LoRA 참조의 병렬 리스트를 모달리티 기준으로 안정 정렬해 [영상…, 오디오…] 순으로 만듭니다. 인코더 출력은 해시와 짝지어 캐시되므로 순서를 바꿔도 안전합니다. 인코더 호출이 14개 단위로 묶이면서 영상당 41 → 13 ms, 클립당 37 → 4 ms, 프리필 3.6 → 1.3 s로 줄었고, 오디오+영상 요청의 지연이 영상만 있는 요청과 같은 수준이 됐습니다.
- MPS 자체의 오버헤드는 작습니다(CPU 디코드 + MPS ≈ CPU 디코드). NVDEC 구성이 64동시에서 약 1 s 느린 것은 API 서버 12개의 CUDA 컨텍스트가 디코드와 동기화를 수행하며 엔진과 GPU를 나눠 쓰기 때문입니다.

## 1080p 라이브 세그먼트

실제 1080p 방송(`2026-worldcup-full-match`, 1920×1080 60fps 8 Mbps)의 80분을 `seg6.ts`의 인코더 특성으로 재인코딩해 6초 TS 800개를 만들었습니다.
- H.264 High, 29.97 fps, B-프레임 2, 세그먼트당 키프레임 1개, AAC 16 kHz 모노. 해상도와 비트레이트(4.5 Mbps, 중앙값 3.55 MB)만 다릅니다.
- 세그먼트마다 내용이 달라 변형 없이 모든 캐시가 빗나갑니다.
- 서버 인자·요청 형식은 360p와 같고 입력만 바꿨습니다.

  - live-ingest는 마스터 플레이리스트의 첫 번째 variant를 고르므로, 1080p가 실제로 들어오는지는 피드의 variant 순서에 달려 있습니다.

## 측정 방법

- **1건 단독**은 요청을 하나씩 순서대로 보냈을 때 한 요청의 소요 시간이고, **64동시 p50**은 64개를 한꺼번에 보냈을 때 각 요청이 응답받기까지 걸린 시간의 중앙값입니다(버스트 3회, 192개 요청).
  - 64개가 함께 처리되어 거의 동시에 끝나므로 p50은 64개 전체를 끝내는 시간(wall)과 거의 같고, 처리량은 64 / wall입니다. 표의 **처리량**은 모두 응답까지 끝난 요청 수 기준(req/s)이며, 디코드만의 처리량(frames/s, clips/s)이 아닙니다. **버스트**는 64개 요청을 한꺼번에 보낸 묶음 1회를 뜻하고, "버스트 1회 동안 … 합계"는 그 묶음이 처리되는 동안 엔진이 해당 단계 호출에 쓴 시간을 모두 더한 값입니다(최댓값이 아님).
- **환경**
  - B200 1장(GPU 0, TP/PP/DP=1), 드라이버 580.126.09, torch 2.13.0+cu130, vLLM 0.28.0, PyNvVideoCodec 2.1.1. Nemotron은 `bench/e2e_matrix.sh`와 같은 서버 인자, Qwen3-Omni는 운영 인자를 사용했습니다.
- **입력**
  - `seg6.ts`(640×360, AAC 16 kHz)를 800개로 복제했습니다. 영상 패킷은 그대로 두고 오디오에만 -80 dBFS 잡음을 넣어 재인코딩했습니다. vLLM은 영상을 바이트로, 오디오를 디코드된 파형으로 해시하기 때문에 둘 다 달라야 프로세서·인코더·프리픽스 캐시를 모두 우회할 수 있습니다. Qwen 측정에서 시스템 프롬프트는 운영과 마찬가지로 프리픽스 캐시에 적중합니다(4,016토큰).
- **집계**
  - 원시 기록을 버스트 시간 창으로 잘라 합계와 분위수를 계산했고, 프로세스·단계별 첫 호출(torch.compile, 디코더 생성)은 워밍업으로 간주해 제외했습니다. 프리필·생성은 vLLM이 요청별로 기록하는 `prefill_time`, `decode_time`입니다. Nemotron 버스트는 3회, Qwen 실험 구성은 2회 반복했으므로 5% 이내의 차이는 잡음으로 봐야 합니다.

## 한계와 후속

- 다운로드는 같은 파드 내 HTTP 서버 기준이라 사내망·스토리지 지연이 포함되지 않습니다. 같은 노드에서 다른 파드가 실행 중이어서 CPU 단계 수치가 실행마다 흔들립니다.

- **후속 1**: 정렬 패치를 서빙 이미지에 포함할지(`nvdec_mpegts.py`와 같은 방식), 업스트림에 제출할지 결정.

- **후속 3**: `REPORT.md`의 "API 서버 12개" 서술과 148행의 서빙 명령(`vllm serve`로 적혀 있으나 실제 스크립트는 `python -m`) 정정. 이 PR에서는 수정하지 않았습니다.
