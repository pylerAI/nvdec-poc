# VOD 14초 장면 클립, 360p·480p·720p·1080p 1~9단계 실측 (2026-10-12)

[10-08 측정](vod14s_stages_2026-10-08.md)(360p vs 1080p)에 480p·720p를 더해, 네 해상도 × 세 구성(운영 그대로 / NVDEC + MPS / NVDEC + MPS + API 서버 12) = 12개 실행을 같은 파드에서 한 세트로 다시 쟀다. 모델·요청 형식·서버 구성·하네스는 10-08과 같다(운영 VOD 엔드포인트와 같은 Qwen3-Omni-30B-A3B-Instruct, vLLM 0.28.0, B200 1장, `worker-captioning` 요청 형식). 다른 점은 파드의 CPU 쿼터가 128코어에서 **32코어**(cgroup `cpu.max`; 운영 limit 16코어에 더 가깝다)로 줄었다는 것이라, 360p·1080p도 이 파드에서 다시 쟀고(`-cpu32`) 10-08 수치와는 "CPU 쿼터" 절에서만 비교한다.

단계별 표 전체는 [vod14s_4res_2026-10-12_stages.md](vod14s_4res_2026-10-12_stages.md), 12개 실행의 요청별 평균 비교는 [vod14s_4res_2026-10-12_compare.md](vod14s_4res_2026-10-12_compare.md), 128 vs 32코어 비교는 [vod14s_4res_2026-10-12_quota_compare.md](vod14s_4res_2026-10-12_quota_compare.md), 원시 데이터는 [vod14s_4res_2026-10-12_raw.tar.gz](vod14s_4res_2026-10-12_raw.tar.gz), 실행 로그와 데이터 생성·체인 스크립트는 [vod14s_4res_2026-10-12_chain.log](vod14s_4res_2026-10-12_chain.log)에 있다.

## 요약

1. **생성(9번)이 네 해상도 모두에서 지배한다.** 운영 그대로(OpenCV) 기준 1건의 67%(1080p)~81%(360p), 운영 배치(8동시)의 64~73%, 64동시의 51~67%다. 해상도가 올라갈수록 비중이 줄지만 생성이 빨라져서가 아니라 디코드·전처리가 늘어서다. NVDEC + API 서버 12 구성에서는 64동시에서도 69~72%로 네 해상도가 같다.
2. **480p부터 영상 토큰 수가 같다.** 운영 `max_pixels 313600`이 프레임을 736×416으로 줄이므로 480p·720p·1080p는 전처리 출력·비디오 토큰(4,186)·프롬프트(8,705토큰)가 같고, 360p만 640×352(프롬프트 7,520)다. 따라서 인코더·프리필·생성 비용은 480p 이상에서 동일하고, 해상도에 따라 늘어나는 것은 디코드(1건 OpenCV 79 → 120 → 196 → 326 ms, NVDEC 54 → 72 → 114 → 207 ms)와 축소 연산(185 → 266 → 290 → 321 ms)뿐이다.
3. **1건 지연은 360p 2.94 s, 480p 3.24, 720p 3.33, 1080p 3.52 s이고, 디코더를 바꿔도 ±0.1 s 안이다.** 360p → 480p의 +0.3 s는 디코드 +41 ms, 전처리(대기 포함) +113 ms가 대부분이고, 프롬프트가 1,185토큰 늘어도 프리필·인코더는 +30 ms뿐이다.
4. **운영 배치(8동시)에서는 디코더가 지연을 바꾸지 않는다.** OpenCV → NVDEC 변화는 360p +7%, 480p −4%, 720p −5%, 1080p −5%로 측정 편차 수준이고, 1080p OpenCV 7.54 s만 눈에 띈다. 처리량은 1.05~1.25 req/s로 디코더보다 해상도(토큰 수)가 정한다.
5. **64동시에서 OpenCV의 손해는 해상도에 비례한다.** p50 23.2 / 28.4 / 30.2 / 37.4 s. NVDEC(API 서버 3)은 24.4 / 25.2 / 25.8 / 29.9 s로 480p −11%, 720p −15%, 1080p −20%이고, API 서버 12까지 더하면 1080p 25.9 s(−31%)로 네 해상도가 22~27 s에 모인다. NVDEC에 API 서버 수를 맞추면 64동시에서 해상도 차이가 사라진다.
6. **API 서버 CPU는 OpenCV가 해상도마다 약 2배씩 늘고 NVDEC은 일정하다.** 64동시 요청당 OpenCV 0.92 / 1.65 / 3.16 / 6.43 cpu-s, NVDEC 0.31 / 0.45 / 0.49 / 0.73 cpu-s. 처리량을 곱하면 OpenCV 구성의 API 서버가 쓰는 코어 수는 8동시에서 360p 1.0, 480p 1.6, 720p 2.6, 1080p 4.9코어, 64동시 버스트에서 2.3 / 3.5 / 6.0 / 10.3코어다. 운영 파드 한도 16코어에서 1080p 버스트는 한도의 2/3를 API 서버(대부분 디코드)에 쓴다.
7. **CPU 쿼터 128 → 32코어의 영향은 1080p OpenCV 64동시에만 크다(28.0 → 37.4 s, +34%).** 나머지 구성은 +5~13%로, 새 파드의 기준선이 조금 느린 것(1건 토큰당 생성 6.8 → 7.0 ms)과 구분되지 않는다. 운영 한도(16코어)에서는 1080p OpenCV의 손해가 이보다 클 것이다.
8. **결론: NVDEC이 필요해지는 경계는 720p다.** 360p는 CPU만 줄고(0.8 → 0.3 cpu-s), 480p는 CPU 1.3~1.7 → 0.5 cpu-s와 64동시 −11%로 선택 사항, 720p부터는 CPU 2.1~3.2 → 0.5 cpu-s와 64동시 −15%로 권장, 1080p는 CPU 3.7~6.4 → 0.7~0.8 cpu-s와 64동시 −20~31%로 필수다. 이 판단은 운영 업로드의 해상도 분포에 달려 있으므로 720p 이상 비중을 먼저 확인하는 것이 후속이다.
9. 12개 실행 7,104건 요청이 모두 성공했다. 10-08에 1080p NVDEC + API 서버 12에서 1건 있었던 400 오류는 이번 NVDEC + API 서버 12 2,368건(네 해상도)에서 재현되지 않았다.

- 64동시의 전처리 대기는 API 서버 3개에서는 디코더와 무관하게 해상도에 비례한다(2.5 → 3.7~4.0 → 4.4~4.9 → 6.8~7.2 s). 12개로 늘리면 0.6~1.3 s가 되지만 요청이 엔진에 한꺼번에 도달해 프리필 대기가 늘어(1080p 0.65 → 4.4 s, 480p 2.6 → 5.2 s), 3 → 12의 순이득은 1080p −4.0 s, 360p −2.0 s, 720p −0.2 s, 480p +1.6 s다. API 서버 수는 4~6개 권장을 유지한다.
- 영상만 요청(오디오 없음)은 모든 구성에서 오디오+영상보다 1건 0.2~0.3 s, 64동시 4~6 s 짧다(오디오 토큰과 그만큼의 생성이 빠짐). 단계별 표 전체 참조.
- 64동시 API 서버 12 구성의 다운로드 p50 0.4~1.1 s(720p·1080p)는 같은 파드의 테스트용 HTTP 서버가 4~7 MB 파일 64개를 동시에 내느라 생긴 병목이다. 운영 MinIO와는 다르다.
- NVDEC + API 서버 12의 GPU 메모리 여유는 1.4~2.3 GB(`nvidia-smi` 관측, 183 GB 중)로 10-08(2.8 GB)보다 작았지만 이번 2,368건에서는 디코드 예외가 없었다. 운영에 쓴다면 `--gpu-memory-utilization`을 낮추는 편이 안전하다.

| 5 전처리 연산 | 185 ms | 266 ms | 290 ms | 321 ms |
| 7 비전 인코더 | 45 ms | 53 ms | 52 ms | 50 ms |
| 8 프리필 LM | 115 ms | 131 ms | 129 ms | 124 ms |
| 9 생성 | 2.40 s (340토큰) | 2.49 s (333토큰) | 2.36 s (342토큰) | 2.32 s (327토큰) |
| 합계 (p50) | 2.94 s | 3.24 s | 3.33 s | 3.52 s |
| 프롬프트 토큰 | 7,520 | 8,705 | 8,705 | 8,705 |
| API 서버 CPU/요청 OpenCV (NVDEC) | 0.80 (0.39) cpu-s | 1.26 (0.51) cpu-s | 2.12 (0.55) cpu-s | 3.73 (0.76) cpu-s |

360p → 480p에서 프롬프트가 1,185토큰 늘지만 프리필 LM은 +16 ms, 비전 인코더는 +8 ms뿐이고, 480p 이상에서는 토큰이 같아 두 단계가 더 늘지 않는다. 디코드와 축소 연산만 해상도를 따라 는다.

## CPU 쿼터 128 → 32코어 (같은 구성, 10-08 세트 vs 이번 세트)

| 구성 | 1건 p50 | 8동시 p50 | 64동시 p50 | 64동시 API 서버 CPU/요청 |
|---|---|---|---|---|
| 360p OpenCV, API 3 | 2.78 → 2.94 s | 5.67 → 5.96 s | 21.2 → 23.2 s (+9%) | 0.95 → 0.92 |
| 360p NVDEC + MPS | 2.80 → 2.96 s | 5.67 → 6.39 s | 21.6 → 24.4 s (+13%) | 0.29 → 0.31 |
| 360p NVDEC + MPS + API 12 | 2.80 → 2.91 s | 5.44 → 5.91 s | 20.9 → 22.4 s (+7%) | 0.34 → 0.40 |
| 1080p OpenCV, API 3 | 3.38 → 3.52 s | 6.87 → 7.54 s | 28.0 → 37.4 s (+34%) | 7.94 → 6.43 |
| 1080p NVDEC + MPS | 3.39 → 3.62 s | 6.64 → 7.20 s | 26.4 → 29.9 s (+13%) | 0.59 → 0.73 |
| 1080p NVDEC + MPS + API 12 | 3.41 → 3.53 s | 6.51 → 6.82 s | 24.3 → 25.9 s (+6%) | 0.67 → 0.77 |

- 1080p OpenCV 64동시만 +34%다. API 서버 3개의 FFmpeg 디코드 스레드가 32코어 안에서 서로 경쟁하면서 프런트엔드가 11.8 → 17.5 s로 늘었다(요청당 CPU는 7.9 → 6.4 cpu-s로 오히려 줄었다. 쿼터에 막혀 스레드가 CPU를 받지 못하고 기다린 시간이 늘어난 것이다).
- 나머지 구성의 +5~13%는 쿼터보다 파드 기준선 차이로 본다: CPU를 거의 쓰지 않는 1건 NVDEC도 +6%이고 토큰당 생성이 6.8 → 7.0 ms다. 그래서 두 세트 사이의 값은 비교하지 않고 세트 안에서만 비교한다.

## 결론: 해상도별 NVDEC 필요성 (운영 VOD, GPU 1장 몫)

| 해상도 | 지연 이득 (8동시 / 64동시) | API 서버 CPU/요청 (OpenCV → NVDEC) | OpenCV 구성의 API 서버 코어 수 (8동시 / 64동시 버스트) | 판단 |
|---|---|---|---|---|
| 360p | 없음 / 없음 | 0.8~0.9 → 0.3~0.4 cpu-s | 1.0 / 2.3 | CPU 절감만. CPU 여유가 있으면 바꿀 이유 없음 |
| 480p | 없음 / −11% | 1.3~1.7 → 0.5 | 1.6 / 3.5 | 선택. 버스트가 잦거나 CPU 한도가 빠듯할 때 |
| 720p | −5% / −15% | 2.1~3.2 → 0.5~0.7 | 2.6 / 6.0 | 권장 |
| 1080p | −5% / −20~31% | 3.7~6.4 → 0.7~0.8 | 4.9 / 10.3 | 필수. 32코어에서도 64동시 +34% 느려짐 |

- 코어 수는 요청당 API 서버 CPU × 처리량(req/s)이다. 엔진 프로세스는 구성과 무관하게 8동시 0.8~0.9, 64동시 0.4~0.5 cpu-s/요청(약 1코어)을 더 쓴다.
- NVDEC을 켜면 API 서버 수도 같이 봐야 한다. 64동시에서 전처리 대기(3개: 2.5~7 s)가 남은 병목이고, 12개는 480p에서는 손해다. 4~6개가 적정이다.
- 가장 큰 몫은 어느 해상도에서든 생성이라, 구조화 출력 오버헤드·출력 토큰 수 같은 live 문서의 1순위 조치가 VOD에도 그대로 적용된다.

## 측정 방법과 한계

- 하네스는 10-08과 같다([bench/live_stage_matrix.sh](../bench/live_stage_matrix.sh), `CLIP_EXT=mp4`, `AUDIO_URL_BASE`). 워밍업 64×4 → 순차 24 → 8동시 2회 → 64동시 2회, 오디오 켬/끔. 12개 실행은 체인 스크립트가 GPU 유휴를 확인한 뒤 순서대로 돌렸다(실행당 약 11분).
- 파드 CPU 쿼터 32코어(보이는 코어 224개). OpenCV의 FFmpeg 스레드는 이 쿼터 안에서 API 서버 3개가 나눠 쓴다. 운영 limit 16코어는 이보다 작다.
- OpenCV + API 서버 12 조합은 측정하지 않았다(운영 OpenCV 구성은 3개 고정). 따라서 API 서버 수의 효과는 NVDEC 구성에서만 분리된다.
- 운영 VOD는 vLLM 레플리카 4개에 분산되므로 이 수치는 "GPU 1장 몫"이다. 8동시가 운영 배치의 근사치이고 64동시는 과부하 조건이다.
- 콘텐츠가 스포츠 중계 한 경기라 장면 종류가 한정된다. 길이 14초는 운영 p90이다. 다운로드는 같은 파드의 HTTP 서버 기준이라 MinIO 지연은 포함되지 않았다.
- NVDEC + API 서버 12 실행의 `vllm.log` 끝에 있는 `EngineDeadError` 트레이스백은 하네스가 서버를 내릴 때 엔진이 먼저 종료되며 남은 것으로, 측정 중의 오류가 아니다(요청 오류 0건).
