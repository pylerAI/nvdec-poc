# 라이브 6초 360p MPEG-TS, 1~9단계 실측 (2026-10-07)

B200 1장(`dgx-b200-01`, GPU 0), vLLM 0.28.0, Nemotron 3 Nano Omni 30B-A3B BF16. 입력은 `seg6.ts`(H.264 High 640×360 29.97fps, AAC 16 kHz 모노, 6.07초)이고 fps 2로 12프레임을 뽑는다. 모든 요청은 캐시를 빗나간다(아래 "측정 방법"). 원시 데이터와 단계별 표 전체는 [live360_2026-10-07_stages.md](live360_2026-10-07_stages.md), [live360_2026-10-07_raw.tar.gz](live360_2026-10-07_raw.tar.gz)에 있다.

## 요약

1. **이전 PoC는 API 서버 1개로 돌았다.** vLLM 0.28.0의 `python -m vllm.entrypoints.openai.api_server`는 `--api-server-count 12`를 무시하고 단일 프로세스(`run_server`)로 뜬다. API 서버 12개는 `vllm serve`일 때만 생긴다(`run_multi_api_server`). [bench/e2e_matrix.sh](../bench/e2e_matrix.sh)도 앞의 방식이라, REPORT의 "API server 12개" 수치는 실제로는 1개짜리였다. 운영 live-ingest 전용 엔드포인트는 `vllm serve`로 띄우므로(아래 "운영 구성") 이 문제는 PoC 측정에만 해당한다.
2. **API 서버를 실제로 12개 띄우면 64동시 p50이 약 8초에서 4.8초로, 처리량이 약 8에서 13 req/s로 좋아진다.** 1개일 때는 그 프로세스의 전처리 스레드 하나가 요청을 줄 세우는 것이 병목이다.
3. **12개일 때 64동시 지연의 주범은 7번 인코더다.** 이 모델은 비디오를 하나씩 순차 인코딩한다(`requires_sequential_video_encoding`). 영상 하나에 약 33 ms이니 64개면 약 2.1초가 직렬로 쌓인다. 버스트 5.0초 중 엔진이 인코더 안에 머문 시간은 3.1초(62%; 비전 2.1 + 오디오 0.6, 영상만은 2.4초로 50%)다. 그동안 GPU SM 사용률은 30~40%대에 머문다. 이 순차 처리는 업스트림 vLLM v0.29~v0.31과 main에도 그대로 있다.
4. **CPU 기준 1위는 5번 전처리다(요청당 80~112 cpu-ms).** 이전 추정치 267 cpu-ms보다 훨씬 작다. 오디오의 프론트엔드 비용은 약 8 cpu-ms로 작고(이전 추정 300 cpu-ms), 오디오의 큰 비용은 GPU 쪽 오디오 인코더(1건 77 ms)에 있다. 다만 이 인코더는 클립 8개를 한 번에 넣어도 약 80 ms라, 64동시에서는 8개씩 묶여 요청당 약 10 ms로 줄어든다.
5. **360p에서 NVDEC은 지연 이득 없이 CPU만 줄인다.** API 서버 CPU가 요청당 0.45에서 0.20 cpu-s로 줄고, p50은 CPU 디코드와 같다.
6. **비디오 인코더를 스텝 단위로 묶는 실험에서 64동시 p50이 4.85 → 3.4 s, 처리량이 13.0 → 18.4 req/s가 됐다.** 출력은 영상별 호출과 비트 단위로 같다(아래 "실험"). 이 순차 처리 제약은 vLLM 0.28.0에서 Nemotron에만 있고, 운영 모델 Qwen3-Omni에는 없다.
7. **운영 모델은 Qwen3-Omni-30B-A3B-Instruct다.** 이 문서의 수치는 Nemotron 3 Nano Omni 기준이므로, Nemotron을 운영 후보로 볼 때의 자료다.

## 파이프라인과 실측값

NVDEC + `vllm serve`(API 서버 12), 오디오+영상, 1건 단독 기준.

```
[live-ingest]  세그먼트 URL(.ts)만 보냄
       │
       ▼  ── API 서버 프로세스 ×12 (vllm serve일 때만; python -m …api_server는 ×1) ──
  1. 다운로드       URL → 바이트. 오디오를 쓰면 같은 URL을 한 번 더 받음       CPU      1.6 ms ×2
  2. 포장 바꾸기    TS → fMP4 스트림카피 (patches/nvdec_mpegts.py)             CPU      4 ms
  3. 디코드         NVDEC이 fps 2로 뽑은 12프레임만 압축 해제                  NVDEC    22 ms
  4. 호스트 복사    12×360×640×3 = 8.3 MB를 핀 메모리로                         GPU→CPU  0.2 ms
  5. 전처리         672×384로 업스케일 + 정규화 → bf16 18.6 MB                  CPU      80~112 ms  ← 서버당 스레드 1개
  6. 오디오         AAC 디코드(PyAV) + 멜스펙트로그램 (원본이 16 kHz)           CPU      ~8 ms
      │  msgpack + ZMQ로 엔진에 전달 (인코딩 0.3 ms)
      ▼  ── EngineCore ×1 (GPU) ──
  7. 인코더         비전 34 ms (영상 1개씩 순차) + 오디오 77 ms                 GPU      ~110 ms
  8. 프리필         1,784토큰 한 번에 (인코더 제외)                             GPU      ~136 ms
  9. 생성           토큰당 6.7 ms (응답 15토큰 = 94 ms)                         GPU
  10. 응답          JSON
```

## 1~9번 중 제일 비싼 단계

같은 구성에서 1건 단독(순차 24요청)과 64동시(64요청 버스트 3회, 192요청 합산)의 값이다. 시간은 경과 시간 중앙값이고, CPU는 그 단계를 실행한 스레드의 CPU 시간이다.

| 단계 | 어디서 | 1건 단독 | 64동시 p50 | 비고 |
|---|---|---|---|---|
| 1 다운로드 | CPU/네트워크 | 1.6 ms × 2회 | 2.1 ms × 2회 | 같은 파드의 HTTP 서버에서 받음. 사내망·스토리지 지연은 미포함 |
| 2 포장 바꾸기 | CPU | 4.3 ms (CPU 4.0) | 46 ms (CPU 14) | 64동시에선 GIL과 미디어 스레드 경합으로 대기가 늘어남 |
| 3 디코드 | NVDEC | 21.7 ms (디코더 재설정·스캔 1.5 + 12프레임 디코드 20.2), CPU 10.6 | 93 ms | CPU(OpenCV)로 하면 50 ms, 프로세스 CPU 152 ms(전체 약 182프레임을 순서대로 디코드하고 11장 사용) |
| 4 호스트 복사 | GPU→CPU | 0.2 ms | 0.3 ms | 8.3 MB |
| 5 전처리 | CPU | 80~112 ms (CPU 동일) | 121 ms, 스레드 대기 포함 362 ms (p95 704 ms) | torch.compile된 bicubic antialias. API 서버마다 전처리 스레드 1개(`_mm_executor`)라 직렬. **CPU 기준 1위** |
| 6 오디오 | CPU | 약 8 ms (2번째 다운로드 1.6 + AAC 디코드 4.3 + 멜 2.1) | 9.5 ms + 멜 2.2 ms | soundfile이 TS를 못 읽어 PyAV로 넘어감(0.1 ms). 16 kHz라 리샘플 없음 |
| 7 인코더 | GPU | 110 ms (비전 34 + 오디오 77) | 스텝당 평균 14개(최대 19개) 묶음, 스텝당 404 ms. 버스트당 비전 64회 2.1 s + 오디오 8회 0.6 s = 3.1 s | 비디오는 1개씩 순차, 오디오는 스텝의 클립을 한 번에. 그동안 엔진 스레드 CPU도 같은 시간 사용(커널 발행 병목 정황) |

| 9 생성 | GPU | 토큰당 6.7 ms (15토큰 94 ms, 59토큰 413 ms) | 0.89 s (토큰당 64 ms) | 64동시에선 새 요청 프리필과 섞여 토큰당 약 10배 느려짐 |
| 합계 | | 0.51 s (프론트엔드+IPC 166 ms) | 4.85 s, p95 4.89 s (프론트엔드+IPC 1.02 s) | 처리량 13.0 req/s |

- **CPU 기준**: 5번 전처리(80~112 cpu-ms)가 요청당 API 서버 CPU(0.17~0.20 cpu-s)의 절반 이상이다. 다음이 디코드 경로(리먹스 포함 프로세스 CPU 18 ms)와 오디오(약 8 ms) 순이다. 디코드를 CPU(OpenCV)로 하면 프로세스 CPU 약 180 ms로 디코드가 1위가 된다.
- **지연 기준, 1건**: 8 프리필 247 ms(이 중 7 인코더 110 ms) > 5 전처리 약 110 ms > 9 생성 94 ms > 3 디코드 27 ms.
- **지연 기준, 64동시**: 엔진이 7 인코더에 머무는 3.1 s(버스트 5.0 s의 62%) > 프론트엔드 1.0 s(이 중 5 전처리가 스레드 대기 포함 0.36 s) > LM 프리필+생성 약 1.9 s.

## 더블 체크

결과를 정리한 뒤 다음을 추가로 확인했다.

- **API 서버 1개**: `vllm/entrypoints/openai/api_server.py`의 `run_server` docstring이 "Run a single-worker API server"이고, 이 파일은 `api_server_count`를 한 번도 읽지 않는다. 12개 분기(`run_multi_api_server`)는 `vllm/entrypoints/cli/serve.py`에만 있다. 실측에서도 `python -m` 구성은 요청 192건이 모두 한 PID로 갔다.
- **인코더 점유율**: 원시 기록에서 버스트 창 안의 인코더 호출 시간을 합산하면 오디오+영상 3.10/3.10/3.11 s(벽시계 5.0 s의 62%), 영상만 2.42/2.42/2.49 s(50%)다. 비전은 매번 64회 × 33 ms, 오디오는 8회 × 80 ms다. API 서버 1개 구성에서는 요청이 하나씩 들어와 오디오 인코더가 26회(1.9 s) 불려 배치 효과까지 사라진다.
- **ViT는 커널 발행 병목으로 보인다**: 비전 인코더 한 호출의 경과 시간, 엔진 스레드 CPU 시간, CUDA 이벤트 GPU 시간이 모두 33 ms로 같다. GPU 연산이 병목이면 GPU 시간이 CPU 시간보다 길어야 한다. 이론 연산량(ViT-H/16, 튜블릿 6개 × 1,008패치 ≈ 10 TFLOP)은 B200에서 10 ms 안팎이다. 오디오 인코더도 클립 1개와 8개가 같은 80 ms다.
- **5번 전처리 마이크로벤치** (같은 함수 `_bicubic_resize_and_normalize`, 12×360×640 → 672×384 bf16):

  | 실행 위치 | 경과 | CPU 시간 |
  |---|---|---|
  | CPU, `OMP_NUM_THREADS=1` (서버 설정과 같음) | 88 ms | 88 cpu-ms |
  | CPU, 2 스레드 | 47 ms | 94 cpu-ms |
  | CPU, 4 스레드 | 28 ms | 111 cpu-ms |
  | CPU, 8 스레드 | 18 ms | 143 cpu-ms |
  | B200 | 0.4 ms (+ 8.3 MB H2D 0.9 ms) | 0.4 cpu-ms |

- **업스트림**: `requires_sequential_video_encoding = True`는 vLLM v0.29.0, v0.30.0, v0.31.0, main에 그대로 있고, 러너 쪽 주석도 "temporary hack"인 채다. RADIO의 `compile_mm_encoder`·CUDA graph 지원은 없다.
- **ViT 배치의 수치 안전성**: RADIO 비디오 경로는 연속 프레임 2장을 튜블릿으로 묶고, 튜블릿들을 한 시퀀스로 이어 붙인 뒤 블록 대각 마스크로 어텐션하며, 위치 인코딩은 공간 전용이다. 따라서 프레임 수가 같고 T의 배수인 영상들은 한 번에 넣어도 결과가 영상별 호출과 같다.

## 실험: 비디오 인코더를 스텝 단위로 묶기

`BATCH_VIDEO=1`로 [bench/stagetime/sitecustomize.py](../bench/stagetime/sitecustomize.py)가 두 가지를 바꾼다. 모델 클래스의 `requires_sequential_video_encoding`을 지워 러너가 한 스텝의 영상들을 한 번의 `embed_multimodal` 호출로 넘기게 하고, `_extract_video_embeddings_temporal`이 프레임 수가 같은(그리고 T=2의 배수인) 영상들을 `extract_feature` 한 번으로 처리하게 한다. 같은 조건(NVDEC, `vllm serve` 12개, 캐시 전부 미스)으로 다시 쟀다. 원시 데이터: [live360_2026-10-07_batchvit_raw.tar.gz](live360_2026-10-07_batchvit_raw.tar.gz), 단계별 표: [live360_2026-10-07_batchvit_stages.md](live360_2026-10-07_batchvit_stages.md).

| | 기존 (영상 1개씩) | 배치 (스텝의 영상을 한 번에) |
|---|---|---|
| 비전 인코더 | 64회 × 33 ms = 2.1 s/버스트 | 8~9회 × 122 ms ≈ 1.0 s/버스트 (영상당 9~15 ms) |
| 64동시 p50 (오디오+영상 / 영상만) | 4.85 / 4.70 s | **3.42 / 3.34 s** |
| 64동시 처리량 | 13.0 / 13.3 req/s | **18.3 / 18.6 req/s** |
| 1건 단독 (오디오+영상 / 영상만) | 0.51 / 0.74 s | 0.48 / 0.69 s (영상 1개라 변화 없음) |
| 출력 차이 (영상 5·14·4개 배치에서 영상별 호출과 비교) | | max abs diff **0.0** |

- 남은 버스트 시간 3.4 s는 대략 LM 프리필·생성 1.8 s, 비전 1.0 s, 오디오 인코더 0.6 s다.
- 조건: 영상 모양과 프레임 수가 같아야 한다. 라이브 360p는 항상 12프레임이라 맞고, OpenCV 디코드(11프레임, 홀수)는 영상별 경로로 되돌아간다. EVS(`--video-pruning-rate`)를 켜면 러너가 `is_multimodal_pruning_enabled`로도 영상을 쪼개므로 그 조건까지 풀어야 한다. 러너의 순차 처리는 EVS를 켠 긴 영상의 최대 메모리를 막으려는 임시 조치라, 6초 세그먼트에서는 해당하지 않는다(`extract_feature`의 128프레임 마이크로배치 상한은 그대로 둔다).

## 운영 구성 (iac 기준)

`pylerAI/iac` `helm/charts/vllm-serving/values.yaml`의 live-ingest 전용 항목 `qwen3-omni-thinker-live-only`:

| 항목 | 값 |
|---|---|
| 모델 | **Qwen3-Omni-30B-A3B-Instruct** (이 문서의 Nemotron이 아님) |
| 이미지 | `shared/vllm-serving:0.4.2` (vLLM 0.28.0 + `nvdec_mpegts.py` 패치, `pylerAI/docker`) |
| 실행 | `entrypoint.sh vllm serve` → `--api-server-count 12`가 실제로 적용됨 |
| 환경 | `ENABLE_MPS=true`, `OMP_NUM_THREADS=1`, `NVIDIA_DRIVER_CAPABILITIES=video,compute,utility` |
| 인자 | `--media-io-kwargs {"video":{"backend":"pynvvideocodec","hw_decoders":2}}`, `--mm-processor-kwargs {"max_pixels":313600,"fps":2.0}`, `--max-num-batched-tokens 49152`, max-model-len 49152 |
| 자원 | B200 1장, CPU limit 16 (request 4), 메모리 128 Gi, `/dev/shm` 16 Gi |

시사점: (1) `python -m` 단일 API 서버 문제는 PoC 측정에만 있었다. (2) `--mm-processor-cache-gb`가 기본 4 GiB인데 API 서버 12개 + 엔진에 각각 잡혀 최대 52 GiB까지 쓸 수 있고, 라이브 세그먼트는 반복되지 않아 이 캐시가 맞을 일이 없다. (3) 별도의 `nemotron-omni-ea` 차트(`maxNumSeqs: 1`, 디버그 모드)가 있는데, 이 문서의 수치를 운영 비교에 쓰려면 Qwen3-Omni로 같은 측정을 다시 해야 한다.

## 측정 방법과 한계

- **환경**: 워크스페이스 파드(B200 4장 중 GPU 0만 사용, MIG 꺼짐), 드라이버 580.126.09. torch 2.13.0+cu130, vLLM 0.28.0, PyNvVideoCodec 2.1.1, PyAV 16.1.0, transformers 5.17.0, OpenCV 5.0.0으로 이전 PoC와 같고, `patches/nvdec_mpegts.py`를 적용했다. NVDEC 구성은 CUDA MPS를 켰다. 서버 인자는 `bench/e2e_matrix.sh`와 같다(`--max-num-batched-tokens 32768`, `max_tokens 64`, `enable_thinking false`).
- **CPU 할당**: 파드 CPU 쿼터가 128코어로 이전(64)과 다르다. 다만 이 부하는 64동시에서도 서버 전체가 4~7코어만 쓰므로 쿼터가 병목이 되지 않는다. 같은 노드에 다른 파드가 돌고 있어서(load average 약 55) 5번 전처리가 실행마다 80~112 ms로 흔들렸다. 스레드 CPU 시간이 경과 시간과 같으므로 대기가 아니라 순수 연산 속도 차이다.
- **입력**: `seg6.ts`를 800개로 복제했다(`bench/make_variants.py`). 영상 패킷은 그대로 복사하고, 오디오는 -80 dBFS 잡음을 넣어 AAC로 재인코딩했다. vLLM은 영상을 인코딩된 바이트로, 오디오를 디코드된 파형으로 해시하기 때문에 둘 다 달라야 모든 캐시(프로세서, 인코더, 프리픽스)를 피한다. 실제로 cached prompt tokens는 0이었고 인코더는 항목마다 실행됐다. NVDEC 프레임은 원본과 바이트 단위로 같다. OpenCV는 TS의 프레임 수를 실제보다 크게 추정해 마지막 샘플을 읽지 못하고 11프레임을 쓴다(원본도 같음).
- **계측**: [bench/stagetime/sitecustomize.py](../bench/stagetime/sitecustomize.py)가 vLLM 함수를 감싸 단계별로 기록한다. GPU 단계는 CUDA 이벤트로 재서 동기화를 추가하지 않았다. 프로세스·단계별 첫 호출은 워밍업(torch.compile, 디코더 생성)으로 보고 제외했다. 프리필과 생성은 vLLM이 요청마다 계산하는 `prefill_time`, `decode_time`이다. 인코더 동안 엔진 스레드 CPU가 GPU 시간과 같은데, 커널 발행이 병목인지 동기화 대기인지는 이 데이터로 구분하지 않았다.
- **부하 형태**: 64동시는 64개를 한꺼번에 보내는 버스트다. 세그먼트가 고르게 도착하는 운영 패턴에서는 대기가 이보다 작다. 버스트에서 잰 처리량 약 13 req/s를 정상 상태 한도로 보면 6초 세그먼트 약 78개 스트림이다.

## 재현

```bash
python bench/make_variants.py /gpfs/private/garam/nvdec-bench-2026-09-17/seg6.ts ~/nvdec-runs/variants 800
NV='{"video":{"backend":"pynvvideocodec","hw_decoders":2,"fps":2,"num_frames":128}}'
CPU='{"video":{"backend":"opencv","fps":2,"num_frames":128}}'
MPS=1 OUT=~/nvdec-runs/live360-nvdec-asc12 bash bench/live_stage_matrix.sh nvdec-asc12 "$NV"
      OUT=~/nvdec-runs/live360-cpu-asc12   bash bench/live_stage_matrix.sh cpu-asc12   "$CPU"
MPS=1 SERVE=module OUT=~/nvdec-runs/live360-nvdec-asc1 bash bench/live_stage_matrix.sh nvdec-asc1 "$NV"
      SERVE=module OUT=~/nvdec-runs/live360-cpu-asc1   bash bench/live_stage_matrix.sh cpu-asc1   "$CPU"
python bench/stage_report.py ~/nvdec-runs/live360-*      # --per-run: 반복 실행을 합치지 않음
```

첫 기동은 FlashInfer가 B200용 MoE 커널을 JIT 컴파일해서 약 19분이 걸린다. 이후 기동은 1.5~3분이다.
