# 라이브 6초 1080p MPEG-TS, 1~9단계 실측 (2026-10-08)

[360p 측정](live360_stages_2026-10-07.md)([Qwen3-Omni](qwen3omni_live360_stages_2026-10-07.md))과 같은 하네스·서버 인자·요청 형식으로 입력만 1080p로 바꿔 다시 쟀다. B200 1장(`dgx-b200-01`, GPU 0), vLLM 0.28.0. 단계별 표 전체는 [live1080_2026-10-08_stages.md](live1080_2026-10-08_stages.md), 원시 데이터는 [live1080_2026-10-08_raw.tar.gz](live1080_2026-10-08_raw.tar.gz), 실행 로그와 세그먼트 생성 명령은 [live1080_2026-10-08_chain.log](live1080_2026-10-08_chain.log)에 있다.

## 요약

1. **1080p에서는 NVDEC이 필수가 된다.** CPU(OpenCV) 디코드는 1080p 180프레임을 전부 디코드하느라 64동시에서 요청당 API 서버 CPU **3.1~3.2 cpu-s**(1건 단독 1.6 cpu-s)를 쓴다. 운영 파드의 CPU limit 16코어에서 5 req/s면 15코어라 CPU 디코드로는 운영이 안 된다. NVDEC은 0.37~0.54 cpu-s다.
2. **지연도 NVDEC이 앞선다.** 360p에서는 CPU 디코드가 같거나 빨랐지만, 1080p 64동시에서는 NVDEC이 Qwen 16.2 vs 18.0 s(−10%), Nemotron 5.52 vs 6.47 s(−15%)로 빠르다. 영상 디코드 비중이 요청의 3~9%(NVDEC) / 5~20%(CPU)로 커졌기 때문이다. 1건 단독은 두 디코더가 같다.
3. **Nemotron은 전처리(5번)가 1건 지연의 41%가 된다.** 1080p를 672×384로 줄이는 CPU 리사이즈가 109 → 353 ms로 3배가 되어(토큰 수는 360p와 같음) 64동시에서는 API 서버당 전처리 스레드 1개에 대기가 쌓여 1.0 s(p95 1.9 s)다. 360p에서 3순위였던 "전처리를 엔진 GPU로"가 Nemotron 1080p에서는 1~2순위다. Qwen은 1080p를 736×416으로 줄이며 118 ms(1건의 4%)라 영향이 작다.
4. **인코더 쪽 개선은 1080p에서도 유지된다.** Qwen 모달리티 정렬 64동시 p50 16.2 → 12.8 s(−21%), Nemotron 배치(batch) 처리 5.52 → 4.29 s(−22%). 출력은 영상별 호출과 비트 단위로 같다(max abs diff 0.0).
5. **Qwen은 여전히 생성이 지배한다.** 1건 2.80 s 중 생성 2.3 s(79%). 1080p에서 내용이 다양해져 출력이 230 → 314토큰으로 길어진 것이 1건 지연 증가(1.92 → 2.80 s)의 2/3를 차지하고, 나머지가 프론트엔드(0.13 → 0.41 s)다. 토큰당 생성 시간(1건 7.0 ms, 64동시 36 ms)은 해상도와 무관하다.

## 테스트 데이터

- 소스: GPFS의 실제 1080p 방송(`2026-worldcup-full-match/ARG_vs_ALG_groupJ_match1.mp4`, 1920×1080 60fps H.264 High 8 Mbps, AAC 48 kHz 스테레오)의 10분~90분 구간. 360p 세그먼트를 업스케일한 것이 아니라 디테일·움직임이 실제 1080p인 콘텐츠다.
- 인코딩: 운영 360p 세그먼트 `seg6.ts`의 인코더 특성을 그대로 복사했다. H.264 High(레벨만 4.0), 29.97 fps, B-프레임 2, 참조 1, 세그먼트당 키프레임 1개(GOP = 6초 전체), AAC-LC 16 kHz 모노 48 kbps. 해상도와 비트레이트만 다르다(4.5 Mbps ABR, 최대 5 Mbps). ffmpeg HLS 세그먼터로 6초마다 IDR을 강제해 잘랐다(명령은 실행 로그 끝에 있다).
- 결과: 세그먼트 800개, 각 180프레임·키프레임 1개·6.0초, 0.8~4.5 MB(중앙값 3.55 MB). 세그먼트마다 내용이 달라 360p 때의 잡음 변형 없이도 모든 캐시가 빗나간다(cached prompt tokens: Nemotron 0, Qwen은 시스템 프롬프트 4,016만 적중).
- 단독 디코드 확인: NVDEC 12프레임 118 ms(리먹스 포함, 프로세스 CPU 56 ms), OpenCV 11프레임 144 ms(프로세스 CPU 1,218 ms). OpenCV가 11프레임을 내는 TS 프레임 수 추정 문제는 360p와 같다.

## 360p 대비 바뀐 것

| 항목 | Qwen 360p → 1080p | Nemotron 360p → 1080p |
|---|---|---|
| 1건 p50 | 1.92 → 2.80 s | 0.51 → 0.88 s |
| 64동시 p50, NVDEC / CPU | 14.6 / 13.5 → 16.2 / 18.0 s | 4.85 / 4.82 → 5.52 / 6.47 s |
| API 서버 CPU/요청 (64동시), NVDEC / CPU | 0.16 / 0.40 → 0.37 / 3.08 cpu-s | 0.20 / 0.45 → 0.54 / 3.23 cpu-s |
| 3 디코드 (1건), NVDEC / CPU | 22 / 55 → 75 / 144 ms | 22 / 53 → 80 / 157 ms |
| 3 디코드 비중 (1건, NVDEC / CPU) | 1.2% / 2.9% → 2.7% / 5.2% | 4.4% / 11% → 9.2% / 17% |
| 5 전처리 연산 (1건) | 45 → 118 ms | 109 → 353 ms |
| 2 포장 바꾸기 (1건) | 4 → 21 ms | 4 → 23 ms |
| 7 인코더 (1건) | 70 → 75 ms (비디오 토큰 1,320 → 1,793) | 111 → 106 ms (토큰 동일) |
| 9 생성 (1건) | 1.63 → 2.3 s (출력 233 → 314토큰) | 94 → 124 ms (15 → 20토큰) |

- 64동시 NVDEC 디코드 423~470 ms 중 절반은 디코더 재설정·스트림 스캔 대기(3a, p95 285~462 ms)다. API 서버당 디코더 슬롯 2개를 두고 5~6개 요청이 줄을 서기 때문이다. 360p에서는 3a가 33 ms였다.
- 64동시에서 생성 토큰당 시간(Qwen 36 ms, Nemotron 53 ms)은 360p와 같다. 해상도는 프론트엔드와 프리필에만 영향을 준다.

## 개선 우선순위 (1080p 기준으로 바뀐 점)

- **NVDEC 유지는 선택이 아니라 필수**: CPU 디코드는 운영 CPU limit을 넘고 지연도 10~15% 나쁘다. MPS도 그대로 필수.
- **Nemotron 전처리 GPU 이관**이 2순위(배치 처리 다음)로 올라간다. 1건의 41%, 64동시 대기 포함 1.0 s. B200에서 같은 연산은 수 ms(75 MB H2D 포함)로 추정된다. 임시로 API 서버 `OMP_NUM_THREADS` 2~4를 두면 353 ms가 100~180 ms로 줄지만 CPU는 더 쓴다.
- Qwen의 순위는 360p와 같다: 구조화 출력 비용 > 모달리티 정렬 > 생성 자체. 전처리는 118 ms(1건의 4%)라 아직 낮다.
- NVDEC 디코더 슬롯 수(`hw_decoders` 2)는 64동시에서 재설정·스캔 대기를 만든다. 360p PoC에서 슬롯 2·4·7이 같았던 것은 GIL 때문이었는데, 1080p에서는 스캔 비용이 커졌으므로 재검토할 가치가 있다(미측정).

## 측정 방법과 한계

- 360p와 같은 하네스([bench/live_stage_matrix.sh](../bench/live_stage_matrix.sh), 단계 타이머, 워밍업 제외, 순차 24건 + 64동시 버스트 기준선 3회·실험 2회). 서버 인자와 요청 형식은 360p 때와 동일하고 `SEG`만 바꿨다.
- 콘텐츠가 스포츠 중계 한 경기라 장면 종류가 한정된다. 운영의 뉴스·드라마 채널과는 출력 길이(생성 토큰)가 다를 수 있다.
- 운영 1080p 렌디션의 실제 인코딩 파라미터는 레포에 없어 360p 세그먼트의 특성을 복사해 가정했다. 특히 fps(29.97 가정)와 GOP(세그먼트당 키프레임 1개)는 디코드 비용에 직접 영향을 준다. live-ingest는 마스터 플레이리스트의 첫 번째 variant를 고르므로, 실제로 1080p가 들어오는지는 피드의 variant 순서에 달려 있다.
- 다운로드는 같은 파드의 HTTP 서버 기준이다. 3.5 MB 세그먼트의 사내망·스토리지 지연은 포함되지 않았다.

```bash

bash ~/nvdec-runs/make_1080p_segments.sh      # 명령 본문은 live1080_2026-10-08_chain.log 끝에 있음
export SEG=~/nvdec-runs/segments-1080p
# Qwen3-Omni 운영 모양 (qwen3omni_live360_stages_2026-10-07.md의 환경변수 그대로)
MPS=1 REPS=3 bash bench/live_stage_matrix.sh qwen1080-nvdec-asc12 '{"video":{"backend":"pynvvideocodec","hw_decoders":2}}'
      REPS=3 bash bench/live_stage_matrix.sh qwen1080-cpu-asc12   '{"video":{"backend":"opencv"}}'
SORT_MM=1 MPS=1 REPS=2 bash bench/live_stage_matrix.sh qwen1080-nvdec-sortmm '{"video":{"backend":"pynvvideocodec","hw_decoders":2}}'

      REPS=3 bash bench/live_stage_matrix.sh nemo1080-cpu-asc12 '{"video":{"backend":"opencv","fps":2,"num_frames":128}}'
BATCH_VIDEO=1 BATCH_VIDEO_CHECK=3 MPS=1 REPS=2 bash bench/live_stage_matrix.sh nemo1080-nvdec-batchvit "$NV"
python bench/compare_runs.py "360p=~/nvdec-runs/qwen-live360-nvdec-asc12" "1080p=~/nvdec-runs/qwen-live1080-nvdec-asc12"
```
