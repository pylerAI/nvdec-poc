# VOD 14초 장면 클립, 360p vs 1080p 1~9단계 실측 (2026-10-08)

운영 VOD 캡셔닝 경로(vuf-poc `worker-captioning`)의 입력·요청 형식·서버 구성으로, 같은 내용의 영상을 360p와 1080p로 만들어 비교했다. 모델은 운영 VOD 엔드포인트와 같은 Qwen3-Omni-30B-A3B-Instruct, B200 1장(`dgx-b200-01`, GPU 0), vLLM 0.28.0. 단계별 표 전체는 [vod14s_2026-10-08_stages.md](vod14s_2026-10-08_stages.md), 원시 데이터는 [vod14s_2026-10-08_raw.tar.gz](vod14s_2026-10-08_raw.tar.gz), 실행 로그와 데이터 생성 명령은 [vod14s_2026-10-08_chain.log](vod14s_2026-10-08_chain.log)에 있다.

## 요약

1. **VOD에서도 생성(9번)이 지배한다.** 14초 클립은 JSON 출력이 320~365토큰이라 1건 지연의 67%(1080p)~80%(360p), 운영 배치(8동시)에서 68~75%, 64동시에서 63~68%가 생성이다. 토큰당 시간은 1건 6.9 ms, 8동시 12 ms, 64동시 42~50 ms로 해상도와 무관하다.
2. **360p는 디코더를 바꿔도 지연이 같다.** 1건 2.78 vs 2.80 s, 8동시 5.67 vs 5.67 s. OpenCV가 360p 420프레임을 다 디코드해도 96 ms(프로세스 CPU 0.45 s)라 묻힌다. NVDEC은 API 서버 CPU를 요청당 0.8~0.95 → 0.3 cpu-s로 줄인다.
3. **1080p는 CPU 디코드가 운영 한도를 위협한다.** OpenCV가 1080p 420프레임을 다 디코드하면 요청당 API 서버 CPU가 1건 3.55, 8동시 4.75, 64동시 7.9 cpu-s다(API 서버 3개의 FFmpeg 스레드 경합). 운영 파드 CPU limit 16코어에서 8동시 1.1 req/s면 코어 5개가 계속 돌고, 그 이상에서는 CPU가 한도를 정한다. NVDEC은 0.6 cpu-s로 1/8이고 지연은 8동시 −3%, 64동시 −6%(API 서버 3개) / −13%(12개)다.
4. **64동시에서는 API 서버 3개의 전처리 스레드가 병목이다.** 전처리(5번)는 연산 자체가 1080p 300 ms, 360p 160 ms인데, 64동시에서는 대기 포함 1080p 5.8 s(p95 10 s), 360p 2.4 s가 된다. API 서버를 12개로 늘리면 1.1 / 0.6 s로 줄지만 요청이 엔진에 한꺼번에 도달해 프리필이 1.0 → 4.1 s(1080p)로 늘어, 64동시 p50은 28.0 → 24.3 s에 그친다. iac 주석이 기록한 "API 서버 1 → 3에서 TTFT 개선"과 같은 축이다. 운영 배치(8동시)에서는 3개로도 대기가 작다(1080p 0.9 s).
5. **오디오를 WAV `audio_url`로 보내는 비용은 작다.** 448 KB 다운로드 + soundfile 디코드 1.2 ms + 멜 5 ms. 오디오 인코더는 클립 1개 33 ms로 live와 같다.
6. **1080p는 360p보다 1건 지연이 0.6 s(22%) 길다.** 디코드 +0.22 s, 전처리 +0.33 s가 대부분이고, 비디오 토큰은 3,080 → 4,186(프롬프트 7,520 → 8,705)이라 프리필은 +0.02 s뿐이다.

## 운영 VOD 경로 (측정에 그대로 사용)

## 테스트 데이터

- 소스: 월드컵 1080p 방송 55분(10~65분 구간). 이를 "업로드 원본" 두 개로 인코딩했다: 1080p(4.5 Mbps)와 640×360(0.6 Mbps), 둘 다 29.97 fps H.264 High, GOP 2초, AAC 48 kHz 스테레오, faststart. 내용이 같고 해상도만 다르다.
- 클립: 운영과 같은 스트림 카피로 14초(p90)씩 230개 × 2해상도. 실제 길이는 키프레임 경계까지 14.1~14.6초(운영도 같음), 첫 프레임은 키프레임. 1080p 7~9 MB, 360p 1.2 MB. 오디오는 운영 `extract_audio`와 같은 16 kHz 모노 WAV(448 KB).
- 클립마다 내용이 달라 캐시가 빗나간다. 230개를 넘겨 재사용되는 요청은 서버가 파일 끝에 요청별 `free` 박스를 붙여 영상 해시만 바꾼다. 시스템 프롬프트(4,016토큰)는 운영처럼 프리픽스 캐시에 적중한다.
- 단독 디코드: 1080p NVDEC 217 ms(프로세스 CPU 65 ms) vs OpenCV 263 ms(CPU 2.5 s); 360p 57 ms(25 ms) vs 81 ms(407 ms). mp4는 프레임 수가 정확해 OpenCV도 28프레임을 낸다.

## 구성별 비교 (오디오+영상)

| 해상도 | 운영 구성에서 바꾼 항목 | 1건 p50 | 8동시 p50 / 처리량 (req/s, 요청 전체) | 64동시 p50 / 처리량 | API 서버 CPU/요청 (1건 / 8동시 / 64동시) |

- 영상만 요청(오디오 없음)은 모든 구성에서 오디오+영상보다 1건 0.2~0.3 s, 64동시 4~6 s 짧다(오디오 토큰과 그만큼의 생성이 빠짐). 단계별 표 전체 참조.
- NVDEC + API 서버 12개 + 1080p에서 591건 중 1건이 디코드 단계 예외로 400 응답을 받았다(일시적, 클립 자체는 정상). 이 구성은 GPU 메모리 여유가 2.8 GB뿐이라 12개 CUDA 컨텍스트와 1080p 프레임(클립당 174 MB)에 빠듯하다. 운영에 쓴다면 `--gpu-memory-utilization`을 낮추거나 재시도가 필요하다.
- 64동시 API 서버 12개 구성의 다운로드 1.1 s(평균)는 같은 파드의 테스트용 HTTP 서버가 7~9 MB 파일 64개를 동시에 내느라 생긴 병목이다. 운영 MinIO와는 다르다.

## 측정 방법과 한계

- 하네스는 live와 같고([bench/live_stage_matrix.sh](../bench/live_stage_matrix.sh)), 입력(`SEG`, `CLIP_EXT=mp4`)과 오디오 전송 방식(`AUDIO_URL_BASE`)만 바꿨다. 워밍업 64×4 → 순차 24 → 8동시 2회 → 64동시 2회, 오디오 켬/끔.
- 운영 VOD는 vLLM 레플리카 4개에 분산되므로 이 수치는 "GPU 1장 몫"이다. 8동시가 운영 배치의 근사치이고 64동시는 과부하 조건이다.
- 콘텐츠가 스포츠 중계 한 경기라 장면 종류가 한정된다. 길이 14초는 운영 p90이며, 비용은 길이에 거의 비례하므로 p50(7초)은 live 6초 결과에 가깝다.
- 다운로드는 같은 파드의 HTTP 서버 기준이라 MinIO presigned URL의 지연·대역폭은 포함되지 않았다.
