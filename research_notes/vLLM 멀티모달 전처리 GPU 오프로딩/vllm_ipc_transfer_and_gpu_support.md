## KQ1. How do multimodal preprocessing outputs travel from an API-server process to EngineCore in v0.28.0 (serialization, sockets, size thresholds), and what does "via shared memory" actually mean?

### Takeaway
By default (`--mm-tensor-ipc direct_rpc`) the HF-processor output (`MultiModalKwargsItem` per media item, carried inside `EngineCoreRequest.mm_features`) is msgpack-encoded by `MsgpackEncoder`, with every tensor ≥ 256 B sent as a raw out-of-line buffer in the same ZMQ multipart message over the client's ROUTER → engine DEALER socket; the engine decodes it zero-copy into CPU tensors that alias the ZMQ frames. There is no shared memory on this path; the only "shared memory" variants are the optional `--mm-processor-cache-type shm` ring-buffer cache (host memory, single API server only) and the optional `--mm-tensor-ipc torch_shm` transport (see KQ3). A CUDA tensor handed to the default encoder is silently copied to host by `tensor_data()`.

### Cited Findings
- `MsgpackEncoder.__init__` takes `size_threshold` defaulting to `envs.VLLM_MSGPACK_ZERO_COPY_THRESHOLD`; the class docstring says "arrays below 256B are serialized inline. Larger will get sent via dedicated messages. Note that this is a per-tensor limit." and "When a `oob_tensor_consumer` is provided, tensors (CUDA and CPU) will be offered to it for out-of-band handling." — [vllm/v1/serial_utils.py:L136-L162](https://github.com/vllm-project/vllm/blob/v0.28.0/vllm/v1/serial_utils.py#L136-L162)

### Inferences
- For the PoC configuration (`--api-server-count 12`), v0.28.0 forces `processor_only` caching: no P1 cache and no shm cache are possible, so every request's `pixel_values_videos` (uint8 after `mm_device_do_normalize`) crosses ZMQ as raw bytes, then is pinned and H2D-copied in the worker (see KQ4). The team's diagram label "via shared memory" is inaccurate for this configuration; the honest description is "msgpack + out-of-band buffers over a ZMQ `ipc://` socket, with a kernel-mediated copy, then a pin + H2D copy in the engine".
- The 128 MiB `mm_shm_cache_max_object_size_mb` default would exclude most multi-frame video tensors from the shm cache even where it is available (single API server); it is a tunable, not a hard limit.

### Gaps
- I did not measure the actual per-request serialization/ZMQ cost in the PoC; the characterizations of overhead come from upstream PR descriptions (#51349, #58461), not from the PoC environment.

## KQ2. What exactly is `vllm/multimodal/gpu_ipc_memory.py`, who calls it, and under which config is it active?

### Takeaway
Despite the "ipc" in its name, `gpu_ipc_memory.py` contains no CUDA-IPC handle code. It is a process-global, blocking byte-counting semaphore (`MultiModalGPUMemoryPool`) that gates how much VRAM the API-server processes may use for GPU video decoding, plus `reserve_mm_ipc_gpu_memory()`, which the engine worker calls to subtract the same budget (and a fixed per-API-server NVDEC decoder + CUDA-context reservation) from the KV-cache budget. It is active only when `--mm-ipc-gpu-memory-gb` > 0 (default 0) and is consulted only by the `pynvvideocodec` video backend.

### Cited Findings
- Module docstring: "Admission control for frontend GPU-side multimodal work. When multimodal media is decoded on the GPU in the API-server (frontend) process, the decoded buffers compete for the same device memory that the engine reserves for weights, activations, and the KV cache. To keep the frontend's GPU usage within a sequestered budget (see `MultiModalConfig.mm_ipc_gpu_memory_gb`), decode paths acquire the number of bytes they need from a process-global `MultiModalGPUMemoryPool` before allocating on the device and release them once the device memory is freed. The pool is a simple byte-counting semaphore … It lives only in the frontend process; the engine carves the matching amount out of its KV-cache budget so the headroom physically exists." — [vllm/multimodal/gpu_ipc_memory.py:L3-L17](https://github.com/vllm-project/vllm/blob/v0.28.0/vllm/multimodal/gpu_ipc_memory.py#L3-L17)
- `MultiModalGPUMemoryPool.acquire(nbytes)` blocks on a `threading.Condition` until `_available >= nbytes`; raises `ValueError` if `nbytes > total_bytes` ("Increase --mm-ipc-gpu-memory-gb or reduce the multimodal input size"). — [vllm/multimodal/gpu_ipc_memory.py:L54-L110](https://github.com/vllm-project/vllm/blob/v0.28.0/vllm/multimodal/gpu_ipc_memory.py#L54-L110)
- `maybe_init_mm_gpu_ipc_pool(mm_ipc_gpu_memory_gb, api_process_count)`: returns `None` when the budget is 0; otherwise `total_bytes = int(mm_ipc_gpu_memory_gb * GiB_bytes) // api_process_count` ("each process gets an equal slice"). — [vllm/multimodal/gpu_ipc_memory.py:L127-L152](https://github.com/vllm-project/vllm/blob/v0.28.0/vllm/multimodal/gpu_ipc_memory.py#L127-L152)
- `reserve_mm_ipc_gpu_memory(available_kv_cache_memory_bytes, mm_config, api_process_count)`: reserves `mm_ipc_gpu_memory_gb` (not multiplied by API-server count) plus, if `mm_config.use_gpu_video_backend()`, `num_api_servers * (PYNVVIDEOCODEC_DECODER_GPU_MEMORY_BYTES * hw_decoders + PYNVVIDEOCODEC_CUDA_CONTEXT_BYTES)`; raises if nothing remains for KV cache. — [vllm/multimodal/gpu_ipc_memory.py:L155-L257](https://github.com/vllm-project/vllm/blob/v0.28.0/vllm/multimodal/gpu_ipc_memory.py#L155-L257)

### Inferences
- With `--api-server-count 12` and e.g. `--mm-ipc-gpu-memory-gb 12`, each API server gets a 1 GiB lease pool (≈ 173 frames of 1920×1080×3 = 6.2 MB each), while the engine additionally subtracts 12 × (2 × 128 MiB + 1.8 GiB) ≈ 24.6 GiB from the KV-cache budget for decoder surfaces/CUDA contexts — a large, mostly fixed cost on a B200 that scales linearly with API-server count. (Arithmetic from the constants and formula cited above.)
- The semaphore covers only decode buffers. If HF preprocessing were moved to the GPU in the API server (KQ3), those allocations would be outside both the engine's profiled budget and this semaphore unless the lease is extended — this is exactly the risk upstream's `validate_mm_processor_device` error message describes.
- The 3× transient over-use reported in #52605 is relevant to a 12-process deployment: per-process peak can exceed its 1/12 slice.

### Gaps
- `PYNVVIDEOCODEC_CUDA_CONTEXT_BYTES` was measured on H100 with PyNvVideoCodec 2.0.4; I found no B200 measurement upstream.

## KQ3. Can v0.28.0 transport a GPU-resident tensor from an API-server process to EngineCore? Under what conditions, and can the team actually produce such a tensor in a co-located deployment?

### Takeaway
Yes, transport exists: `--mm-tensor-ipc torch_shm` plugs a `TensorIpcSender` into `MsgpackEncoder` as the out-of-band consumer; tensors are `share_memory_()`'d and put on a `torch.multiprocessing` Queue (CUDA tensors therefore travel as CUDA-IPC handles, CPU tensors as shared memory), and `EngineCoreProc` drains the queue via `TensorIpcReceiver`. Hard conditions: `VLLM_WORKER_MULTIPROC_METHOD=spawn`, `world_size_across_dp == 1` (no TP/PP/DP), single engine (queue targets rank 0), and the usual PyTorch CUDA-IPC rules; multiple API servers are supported. However, v0.28.0 gives a co-located (non-EPD) deployment no sanctioned way to *produce* a GPU-resident `pixel_values`: the NVDEC backend copies frames to pinned host unconditionally, and `validate_mm_processor_device` raises if `device=cuda` is requested on an instance that also runs the language model. GPU-resident preprocessing is only permitted on an EPD encode-only (EC-producer) instance.

### Inferences
- Clear yes/no: **Transport = YES** in v0.28.0 (`torch_shm`), applicable to the PoC's topology (TP=1, DP=1, 12 API servers, single engine), provided `VLLM_WORKER_MULTIPROC_METHOD=spawn` and both API servers and EngineCore can open each other's CUDA IPC handles on the same physical GPU (under MPS both are MPS clients; I found no NVIDIA statement forbidding CUDA IPC between MPS clients on datacenter GPUs, and the upstream prototype ran that way on H100). **Producing a GPU tensor = NO (without patches)** in a co-located deployment: (a) `_decode_to_pinned_host` always round-trips to host, and (b) `validate_mm_processor_device` rejects `device=cuda` unless `ec_role=ec_producer` without consumer. The stated upstream rationale is memory accounting and SM contention, not a technical impossibility.
- In the PoC's `processor_only` cache mode, the "pathway is only used when the processing cache is disabled" caveat from #32104 does not bite: items are never replaced by `None`, so every tensor would go through the queue. In single-API-server `lru` mode the P1 `MultiModalReceiverCache` would retain the IPC-received CUDA tensors in engine memory for up to `mm_processor_cache_gb` — GPU memory that is not part of the engine's profiled budget (inference from `MultiModalReceiverCache` storing `mm_item` and `_postprocess_output` keeping device tensors).
- The minimal local patch set to go GPU end-to-end on 0.28.0 would be: return `device_frames` (CUDA uint8 NHWC) from the NVDEC backend instead of `host_frames.numpy()`; let the HF/video processor accept tensor frames with `device="cuda"`; relax `validate_mm_processor_device`; run with `--mm-tensor-ipc torch_shm`, spawn, and a `--mm-ipc-gpu-memory-gb` budget that also covers preprocessing outputs. Upstream has since implemented exactly this shape, but gated to EPD encode-only instances (KQ6, PR #53675) and via torchcodec rather than pynvvideocodec.
- Whether Nemotron-3-Nano-Omni's processor honours `device=` is undetermined: the `--mm-processor-device` help restricts the effect to HF "fast" (torchvision) processors, `NanoNemotronVLProcessingInfo.get_hf_processor` returns a custom `NanoNemotronVLProcessor`, and open PR #57924 (2026-09-21) "[MM] Move Nemotron VL image normalization to device" indicates Nemotron VL preprocessing was still being adapted for device-side work after v0.28.0. — [vllm/model_executor/models/nano_nemotron_vl.py:L200-L201,L361-L364,L910](https://github.com/vllm-project/vllm/blob/v0.28.0/vllm/model_executor/models/nano_nemotron_vl.py#L200-L201); [PR #57924](https://github.com/vllm-project/vllm/pull/57924)

### Gaps
- No upstream statement or test covers `torch_shm` + CUDA tensors under CUDA MPS specifically (the CUDA tests do not set up MPS); NVIDIA's docs only exclude Tegra. This needs an empirical check on the B200 box.
- The PyTorch "sender must keep the tensor alive" rule vs. vLLM dropping the sender's Python reference after `queue.put` (the P0 `processor_only` cache may keep it alive incidentally) is not discussed anywhere upstream; I could not find a bug report either way.
- I did not find documentation of what happens to a `torch_shm` CUDA tensor on the queue if the engine is still draining a previous message when the 10 s `queue.put(timeout=10.0)` expires (the code falls back to host serialization, which copies).

## KQ4. On the EngineCore/worker side, how do mm kwargs reach the GPU, where does the encoder run, what caches exist, and could an API-server-produced GPU tensor be consumed without a host round-trip?

### Takeaway
In the worker, `_execute_mm_encoder` groups the scheduled items' `MultiModalKwargsItem`s and calls `group_and_batch_mm_kwargs(mm_kwargs, device=self.device, pin_memory=PIN_MEMORY)`, which (via `reduce_data`) pins CPU tensors and `.to(device, non_blocking=True)`s them; tensors already on the accelerator skip pinning and the device move is a no-op. The encoder (`model.embed_multimodal`, or an encoder CUDA graph) runs in the GPU worker, which for TP=1 is the EngineCore process itself; outputs are cached per `mm_hash` in `self.encoder_cache` (GPU) under the scheduler's `EncoderCacheManager` token budget. So a CUDA tensor that arrives via `torch_shm` would be consumed with no host round-trip; `mm_encoder_tp_mode` only controls TP sharding of the encoder.

### Inferences
- For TP=1 the "EngineCore → GPU" hop is intra-process (`UniProcExecutor`, see KQ3), so a torch_shm-delivered CUDA tensor is consumed directly by `embed_multimodal`: the only remaining work is `reduce_data`'s stack/unsqueeze on-device. The host round-trip in the PoC is therefore entirely on the P0 side (NVDEC D2H + CPU HF processor + ZMQ + pin + H2D), not in the engine.
- Under `direct_rpc`, the per-request host-side cost sequence in the engine is: zero-copy ZMQ-frame view → `pin_memory()` copy → async H2D — two copies plus the P0-side D2H and ZMQ copies.

### Gaps

## KQ5. What does the v0.28.0 NVDEC (`pynvvideocodec`) path look like end-to-end, and what changed on `main` / later releases?

### Takeaway
In v0.28.0 the `pynvvideocodec` backend writes the bytes to a temp `.mp4`, decodes the sampled frame indices with NVDEC on device index 0 of the API-server process (a pool of `hw_decoders` decoder slots, each on its own CUDA stream), converts to NHWC uint8 and copies to pinned host memory inside a `MultiModalGPUMemoryPool` lease, returning a numpy array; the HF processor then runs on CPU. On `main` (checked 2026-10-07) the pynvvideocodec backend still does the same host copy; the GPU-resident path merged later (PR #53675, v0.30.0) is the **torchcodec** backend with `device="cuda"`, auto-selected only on EPD encode-only instances whose processor already runs on CUDA.

### Inferences
- Upstream's chosen vehicle for "frames stay on GPU" is torchcodec (`device="cuda"`), not pynvvideocodec; the pynvvideocodec backend's VRAM semaphore and MPS requirement remain tied to the host-copy design. - Because `_DEVICE_INDEX` is hard-coded to 0, in a multi-GPU box with `CUDA_VISIBLE_DEVICES` set per process, all API servers decode on the first visible device of their own process; the engine's reservation assumes that is the engine's device.

## KQ6. What upstream RFCs/PRs/issues exist on GPU-side preprocessing and Encoder-Prefill-Decode (EPD) disaggregation, and what is their status as of the v0.28.0 commit (2026-08-24) and later?

### Takeaway
Upstream's direction is explicit and consistent: GPU preprocessing and zero-copy NVDEC are being delivered **inside the EPD encode-only instance**, built on `torch_shm` + `--mm-processor-device` (PR #50390, merged 2026-08-05, in v0.28.0) and torchcodec NVDEC (PR #53675, merged 2026-09-11, in v0.30.0). The original NVIDIA proposal to do this in a co-located single-GPU deployment (RFC #30839 / draft PR #31925) landed only its transport (#32104) and VRAM semaphore (#44465) pieces; the TP-aware GPU transport (#49462) and paged-shm cache (#51349) are still open. The Q3 2026 roadmap has no line item on multimodal preprocessing or EPD; EPD work is tracked in issue #52409.

### Inferences
- The maintainers' accepted architecture for "GPU end-to-end multimodal preprocessing" is EPD: a dedicated encode-only vLLM instance (`ec_producer`, `--mm-encoder-only`, `--mm-tensor-ipc torch_shm`, processor on CUDA, torchcodec NVDEC) that publishes embeddings over an EC connector, with the LLM instance receiving only metadata/embeddings. For a single-B200 deployment this would mean running two vLLM instances on one GPU (encoder + PD) — feasible with MPS but it changes the memory split and adds a proxy; the merged connectors in v0.28.0 are disk (`ECExampleConnector`) and host-mmap (`ECCPUConnector`), with NIXL/Mooncake arriving in v0.30.0.
- The co-located, single-process-engine variant the PoC wants (NVIDIA's RFC #30839 design) stalled upstream after its infrastructure pieces merged; the blocking concern recorded in #44465 ("One issue must be discussed with the community first") and in the `validate_mm_processor_device` message is memory accounting / contention in the API-server process. A PoC patch set that re-enables `device=cuda` outside EPD would be swimming against that decision unless it also solves the accounting (e.g., by extending the VRAM semaphore to cover preprocessing outputs).
- Of the measurable gains upstream reported, GPU preprocessing contributed far more than zero-copy NVDEC (#53675 ablation: +220% vs +54%), which suggests prioritizing moving the HF transform to GPU over eliminating the frame D2H copy.

### Gaps
- No upstream RFC, issue or roadmap entry proposes GPU preprocessing for *co-located* (non-EPD) deployments after #44465; I found no explicit "won't do" either — only the config error message and the EPD-only gating.
- I could not retrieve the full benchmark tables of #49462 (body truncated at 5,000 chars in my fetch) or the Google design doc referenced by `disagg_encoder.md`.
- The EPD tracker lists an XPU encoder-only runner (#59320) and MRv2 encoder-only CUDA graphs (#56922); I did not check which of these are merged in v0.31.0.
