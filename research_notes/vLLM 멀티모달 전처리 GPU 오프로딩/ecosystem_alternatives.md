# Ecosystem survey: GPU-side multimodal preprocessing (video resize/normalize/patchify, audio log-mel) for LLM serving, and its fit for vLLM's multi-API-server process model

Scope note: researched 2026-10-07. Team context: Nemotron-3-Nano-Omni-30B-A3B-Reasoning-BF16 on vLLM 0.28.0, one B200, 12 API-server processes sharing the GPU via CUDA MPS; NVDEC decode via PyNvVideoCodec already in each API server, but frames are copied to host and preprocessed on CPU by the HF processor; audio log-mel on CPU. PoC numbers: 1080p RGB frame = 6.2 MB; 120 s clip at 1 fps = ~121 frames = ~750 MB raw per request. Latest releases at time of writing (GitHub `releases/latest`): transformers v5.19.0 (2026-10-06), torchcodec v0.17.0 (2026-09-30), CV-CUDA v0.18.0 (2026-09-16), DALI v2.3.0 (2026-08-28), SGLang v0.5.21 (2026-10-02), TensorRT-LLM v1.2.1 (2026-04-20, docs track 1.3.0rc), Dynamo v1.5.1 (2026-10-07), vLLM v0.31.0 (2026-10-05).

## Key Question 1: Hugging Face transformers fast image/video processors on GPU (`device="cuda"`, GPU tensors, speedups, caveats)

### Takeaway
Since mid-2024 (fast image processors, v4.42) and May 2025 (`BaseVideoProcessor`, v4.52) transformers' torchvision-v2-based processors accept a `device` argument and CUDA tensor inputs, run the whole batch on GPU and can be `torch.compile`d; HF documents "up to 33x faster than the PIL backend". Caveats that matter for serving: outputs are not bit-identical to PIL/slow processors (documented drift that shifted Qwen3-VL bbox outputs), whole-video device placement can spike GPU memory (HF moved placement to after frame sampling in v4.53), and the Nemotron Omni image processor deliberately stays on PIL for bicubic-resize parity, while its video processor is torch/torchvision-native and device-aware.

### Cited Findings
- Fast image processors are "based on the torchvision library and provide a significant speed-up, especially when processing on GPU"; "when using a fast image processor, you can also set the `device` argument ... By default, the processing is done on the same device as the inputs if the inputs are tensors, or on the CPU otherwise"; benchmarks were run on an AWS g5.2xlarge with an NVIDIA A10G; `use_fast` "will be set to True by default in a future release" (v4.56 docs) — [HF docs v4.56.0 image_processor](https://huggingface.co/docs/transformers/v4.56.0/main_classes/image_processor)
- `BaseImageProcessorFast.preprocess(...)` exposes `return_tensors='pt'`, `device=torch.device`, `disable_grouping=bool`, and a `compile_friendly_resize()` helper for uint8 tensors under torch.compile — [HF docs v4.56.0 image_processor](https://huggingface.co/docs/transformers/v4.56.0/main_classes/image_processor)
- Current (v5) docs describe two backends, `TorchvisionBackend` (default when torchvision is installed) and `PilBackend`; the torchvision backend is "GPU-accelerated and up to 33x faster than the PIL backend for batches of torch.Tensor inputs"; "Processing is performed on the same device as the input by default if the inputs are tensors, otherwise it falls back to CPU" — [transformers main docs image_processors.md](https://github.com/huggingface/transformers/blob/main/docs/source/en/image_processors.md)
- The first fast image processor PR ("Fast image processor", #28847) merged 2024-06-11 — [PR #28847](https://github.com/huggingface/transformers/pull/28847); transformers v4.42.0 was released 2024-06-27 — [GitHub releases API](https://github.com/huggingface/transformers/releases). Fast DETR-family processors followed (RT-DETR fast #34354 merged 2024-10-30, Deformable DETR #34353 merged 2024-11-19), plus "Fall back to slow image processor ... when no fast processor available" (#34785, 2024-12-15) and a compile test for fast image processors (#35184, 2024-12-23) — [GitHub search](https://github.com/huggingface/transformers/pulls?q=is%3Apr+%22fast+image+processor%22+in%3Atitle)
- Video processors: "Fast video processors are available for all models and are loaded by default when an `AutoVideoProcessor` is initialized"; "Fast processors handle the whole batch of videos at once, without iterating over each video or frame"; `AutoVideoProcessor.from_pretrained(..., device="cuda")` then `processor = torch.compile(processor)` is the documented recipe "For even more speed improvement" — [HF docs v5.14.0 video_processors](https://huggingface.co/docs/transformers/v5.14.0/video_processors)
- `BaseVideoProcessor` was introduced by PR #35206 "Video processors as a separate class", merged 2025-05-12 (described by its author as "quite a breaking PR": separate `video_preprocessor_config.json`, separate base class for VLM video processors) — [PR #35206](https://github.com/huggingface/transformers/pull/35206); the v4.52 line was released 2025-05-20 (v4.52.1) — [GitHub releases API](https://github.com/huggingface/transformers/releases)
- In `video_processing_utils.py` the device move happens in `_prepare_input_videos` ("if device is not None: video = video.to(device)") after channel inference and RGB conversion; inputs may be numpy arrays or torch tensors (CUDA tensors are used directly); videos are grouped by shape (`group_videos_by_shape`) for resize and again for crop/normalize, then reordered; transforms come from `torchvision.transforms.v2.functional`; `num_frames` and `fps` are mutually exclusive; frame sampling happens before the device move for array inputs — [transformers main video_processing_utils.py](https://github.com/huggingface/transformers/blob/main/src/transformers/video_processing_utils.py)
- Qwen2-VL video processor: `smart_resize` keeps H/W divisible by `factor` and total pixels within `[min_pixels, max_pixels]`; `patchify` pads to `temporal_patch_size` and reshapes to `(batch, grid_t*grid_h*grid_w, channel*temporal_patch_size*patch_size*patch_size)` with plain torch ops, so patches stay on the input tensor's device; returns `pixel_values_videos` and `video_grid_thw` — [transformers main video_processing_qwen2_vl.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen2_vl/video_processing_qwen2_vl.py)
- PR #38880 (merged 2025-06-25, shipped in v4.53.0 on 2025-06-26) added torchcodec loading and noted "a high GPU memory spike with long videos, because we moved the whole video to GPU before processing. This PR moves the device-placement after sampling so only the sampled frames are on device"; it also states "we don't use torchcodec to its fullest, i.e. loading to device or streaming. Loading to device incurs high memory usage because we load the whole video and sampling only after that" — [PR #38880](https://github.com/huggingface/transformers/pull/38880)
- PR #41218 (merged 2025-10-01) lets video processors accept "a 3D tensor on cuda device" (single frames on CUDA) — [PR #41218](https://github.com/huggingface/transformers/pull/41218)
- Numerical caveat: after the image-processor backend refactor (#43514), `Qwen2VLImageProcessorFast` (removed in 5.5.4) was replaced by `Qwen2VLImageProcessor(TorchvisionBackend)`; both use torchvision BICUBIC and identical normalization but produce `pixel_values` differing at the 5th–6th decimal (mean 0.5669328 vs 0.5669392), which "gets amplified into ~20-unit coordinate shifts in 0-1000 normalized" bbox outputs for Qwen3-VL-32B served via SGLang (transformers 4.57.1 vs 5.5.4) — [Issue #46688, opened 2026-06-16, closed 2026-07-24](https://github.com/huggingface/transformers/issues/46688)
- Related upstream fixes: "Use torchvision's native LANCZOS interpolation instead of PIL fallback" (#46496, 2026-06-08) and "Keep image processor backends in sync on keys and dtypes" (#48739, 2026-09-21) — [GitHub search](https://github.com/huggingface/transformers/pulls?q=is%3Apr+LANCZOS+OR+%22image+processor+backend%22)
- `AutoProcessor` eagerly loads the video processor, so image-only VL use requires torchvision (issue #48558, 2026-09-06) — [Issue #48558](https://github.com/huggingface/transformers/issues/48558)
- Nemotron-3-Nano-Omni's HF repo: `image_processing.py` subclasses `BaseImageProcessorFast` but keeps the PIL image through `_preprocess` because "we need PIL.resize (bicubic) to match vLLM's algorithm exactly; resizing a tensor via torchvision.transforms.Resize uses different" kernels ("PIL's bicubic uses a different kernel (and no antialiasing), producing visibly different" results); `video_processing.py` subclasses `BaseVideoProcessor`, takes a `device` kwarg, samples frames first, then `videos = [video.to(device) for video in videos]`, resizes with torchvision `F.resize`, and normalizes with mean/std tensors created on `stacked_videos.device` — [image_processing.py](https://huggingface.co/nvidia/Nemotron-3-Nano-Omni-30B-A3B-Reasoning-BF16/blob/main/image_processing.py), [video_processing.py](https://huggingface.co/nvidia/Nemotron-3-Nano-Omni-30B-A3B-Reasoning-BF16/blob/main/video_processing.py)

### Inferences
- For this model, the video path (`BaseVideoProcessor` subclass with torchvision resize + tensor normalize) can run entirely on GPU today by passing a CUDA frame tensor plus `device="cuda"`; the image path cannot without changing the model's own PIL-bicubic choice, which NVIDIA justified by vLLM parity. Any GPU image path needs a numerical-equivalence check (the Qwen3-VL bbox drift shows 1e-5 pixel differences can be visible downstream).
- HF's own change (#38880) to move to device only after sampling is exactly the pattern needed for the 750 MB/request case: sample 121 frames on the decoder, then resize on GPU, rather than materializing full clips on device.
- The processor is a plain nn-module-like callable; `torch.compile` and the shape-grouping mean dynamic shapes (variable video sizes) will trigger recompiles or fall back; grouping only batches videos of identical shape.

### Gaps
- I could not pin the exact transformers version where the `device` kwarg first appeared on fast image processors (the v4.46.0 docs page I fetched does not document it; it is documented by v4.48.1 and v4.56). Treat "v4.47/v4.48 era (late 2024)" as approximate.
- No HF-published number for video-processor GPU speedups; the only HF speedup figure is the "up to 33x vs PIL" image statement and the A10G DETR benchmark chart (not numerically extracted).
- No HF documentation on numerical tolerances between torchvision-backend and PIL-backend processors; only the user-reported Qwen3-VL case.

## Key Question 2: NVIDIA GPU decode + preprocess tooling (PyNvVideoCodec, torchcodec, DALI, CV-CUDA, nvImageCodec): maturity, Python API, in-process use, memory footprint for 12 processes

### Takeaway
All five libraries run inside an existing process on the CUDA primary context and interoperate with torch via DLPack/`__cuda_array_interface__`; none requires its own process. The practical issues are per-process footprint (vLLM measured ~1.8 GiB of CUDA context + driver allocation per API server with PyNvVideoCodec 2.0.4 on H100, and gates frontend GPU work with a byte-counting pool carved out of KV-cache memory), DLPack format limits in PyNvVideoCodec (NV12 in older versions, RGB/RGBP output types in 2.x), and that torchcodec/DALI/CV-CUDA each add a second resize implementation whose output differs from PIL/torchvision.

DALI
- `nvidia.dali.fn.decoders.video` (stable, no longer under `experimental` in DALI 2.x): `cpu` backend decodes VP8/VP9/MJPEG via libavcodec, `mixed` backend adds AV1/MPEG-4/H.264/H.265 via the NVIDIA Video Codec SDK (NVDEC); input is an in-memory encoded stream; output is `(F, H, W, C)` uint8; frame selection by `frames` (arbitrary order, duplicates allowed), `start_frame/end_frame/stride`, or `start_frame/sequence_length/stride`; `pad_mode` options; `build_index` (default True) caches frame metadata for seeking at extra memory cost — [DALI docs fn.decoders.video](https://docs.nvidia.com/deeplearning/dali/user-guide/docs/operations/nvidia.dali.fn.decoders.video.html)
- DALI memory model: device memory comes from "stream-aware pools on CUDA VMM" (alternatives `cudaMallocAsync` or plain `cudaMalloc`), pinned memory from stream-aware pools; GPU/pinned buffers only grow ("DALI avoids reallocating GPU and pinned memory"); `prefetch_queue_depth` default 2 multiplies buffered batches; `PreallocateDeviceMemory(bytes, device_id)`, `ReleaseUnusedMemory()`, `bytes_per_sample_hint`, `DALI_MAX_IMAGE_SIZE` are the controls — [DALI performance tuning](https://docs.nvidia.com/deeplearning/dali/user-guide/docs/advanced_topics_performance_tuning.html)
- DALI Proxy exists because "GPU data processing occurs in the process running the main loop, which avoids performance degradation caused by multiple CUDA contexts for the same GPU" (i.e., DALI itself is designed to be co-located in the framework process, not in dataloader worker processes) — [DALI PyTorch DALI Proxy](https://docs.nvidia.com/deeplearning/dali/user-guide/docs/plugins/pytorch_dali_proxy.html)
- CUDA runtime semantics behind in-process co-existence: "the specific context which the CUDA Runtime API uses for a device is called the device's primary context"; `cudaSetDevice()` "initializes the primary context for the specified device and makes it current to the calling thread" — [CUDA Runtime API: Interactions with the Driver API](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__DRIVER.html)

nvImageCodec
- GPU image (JPEG etc.) decode with batch `decode()` over lists of files/bytes; decoded images expose `__cuda_array_interface__` so `torch.as_tensor()` wraps them without a copy; DataLoader sample recommends submitting a whole batch to the GPU decoder "in a single call" to avoid per-image CPU/GPU sync — [nvImageCodec Python samples](https://docs.nvidia.com/cuda/nvimagecodec/samples/python_samples.html), [nvImageCodec with Torch](https://docs.nvidia.com/cuda/nvimagecodec/samples/torch.html), [DataLoader integration](https://docs.nvidia.com/cuda/nvimagecodec/samples/torch_dataloader.html)
- SGLang uses `torchvision.io.decode_jpeg(..., device="cuda")` as its default GPU image decode (`gpu_image_decode = True`) — [SGLang issue #42511](https://github.com/sgl-project/sglang/issues/42511)

### Inferences
- The team already pays the dominant fixed cost (a CUDA context plus PyNvVideoCodec decoder state per API server). Adding torchvision-v2/CV-CUDA resize+normalize to the same process adds kernels and transient activations, not another context. The transient size is the issue: 121 frames x 6.2 MB = 750 MB uint8 per request; converting to fp32 before resize quadruples it (~3 GB) unless resize is done in uint8 first (HF `compile_friendly_resize` does uint8 resize) or per-chunk.
- DALI's own memory pools (per process, grow-only, prefetch depth 2) make it the heaviest option for 12 processes; CV-CUDA and torchvision v2 ops allocate through PyTorch's caching allocator (torchvision) or the caller's stream (CV-CUDA via `as_tensor`), which is easier to bound and to release.
- torchcodec's `nvdec` backend with decoder-side `transforms` (resize at decode time, before RGB conversion to full-resolution) is the closest off-the-shelf "decode+resize on GPU in one step" path, but vLLM upstream chose PyNvVideoCodec and declined the torchcodec device option (PR #56333 unmerged).
- Numerical parity: every GPU option (torchvision tensor resize, CV-CUDA resize, NVDEC color conversion) differs from PIL bicubic/CPU paths at the sub-LSB to ~0.4 uint8 MAE level; a model-level accuracy check (not just pixel diff) is required before switching.

### Gaps
- NVIDIA's PyNvVideoCodec programming guide pages did not render through the fetch tool, so I could not confirm the official API for passing an existing CUDA context/stream (`cudacontext`/`cudastream` arguments) or whether 2.2.x lifted the "DLPack NV12-only" limit; vLLM's integration does use `torch.from_dlpack` plus its own stream per decoder slot, which implies in-process primary-context use works.
- No published per-process memory figure for CV-CUDA or nvImageCodec; the only measured per-process number found is vLLM's 1.8 GiB (context + driver) for the PyNvVideoCodec frontend on H100.
- No source found that benchmarks DALI/CV-CUDA/torchvision resize throughput for LLM-serving-style video (1 fps sampled 1080p frames); the available numbers are HF's image numbers (vLLM PR #50390: 2048^2 image 11.46 ms CPU vs 4.32 ms GPU) and the torchcodec/PyNvVideoCodec decode numbers.

## Key Question 3: How SGLang, TensorRT-LLM and NVIDIA Dynamo handle multimodal preprocessing (CPU vs GPU, process boundaries, embedding transport)

### Takeaway
SGLang is the only engine that runs HF fast image/video processors on the GPU by default inside its frontend (tokenizer-manager) process on `cuda:{base_gpu_id}`, with GPU JPEG decode, torchcodec NVDEC video decode, and a CUDA-IPC/VMM pool (`mm_feature_transport`) to hand GPU-resident `pixel_values` to the scheduler; it has since had to add worker-count caps and CPU fallbacks because that competes with the scheduler's GPU. TensorRT-LLM keeps the HF processor on CPU in a frontend thread pool (default 8 workers) and overlaps it with GPU encoding, passing tensors between processes via torch CUDA-IPC/shared-memory handles. Dynamo moves the whole encoder into a separate GPU "encode worker" (E/PD, E/P/D), transfers embeddings over NIXL (RDMA), and decodes H.264/H.265 with PyNvVideoCodec/NVDEC in that worker.

### Cited Findings
SGLang

### Inferences
- Every stack that moved preprocessing to GPU (SGLang in-frontend; vLLM EPD encoder; Dynamo encode worker) did so either on a GPU that is not running the LLM (encoder-only instance) or had to add admission control (SGLang's per-worker pool budget and 1-worker cap; vLLM's `mm_ipc_gpu_memory_gb` carve-out). The 12-API-server-on-one-B200 layout is the hardest case for the in-frontend approach: SGLang's problems (OOM at the margin, device contention) multiply by 12 unless the budget is centrally capped.
- TensorRT-LLM's choice (CPU preprocessing overlapped with GPU encoding, CUDA-IPC transport only for tensors already on GPU) is the conservative design; its measured pathology (PyTorch intra-op oversubscription in frontend threads: 77–97 ms vs 6–9 ms per image) is a cheap thing to check on the current CPU path before investing in GPU preprocessing.
- No engine computes video preprocessing on GPU inside the model forward; all keep an explicit "processor" stage. The only GPU-side "in-model" shift seen is embedding caching/transfer (Dynamo NIXL, vLLM EC connector).

### Gaps
- SGLang's user-facing docs page for server arguments does not list `--image-processor-backend`, `--mm-feature-transport`, or the GPU-decode knobs (only `--enable-multimodal`, media allowlists); defaults were taken from code and issues, not docs.

## Key Question 4: vLLM upstream discussion on GPU preprocessing / CPU bottlenecks (lightweight cross-check)

### Takeaway
Upstream vLLM has (a) a GPU video decode backend (PyNvVideoCodec) that still copies frames to pinned host, (b) `--mm-processor-device={auto,cpu,cuda}` (merged 2026-08-05) that runs the HF processor on GPU only on EPD encoder-only instances with `--mm-tensor-ipc=torch_shm`, (c) an open PR for a `cuda_ipc` TP-aware GPU transport, and (d) open RFCs for a preprocessing sidecar and EPD tracking; the recurring theme in issues is CPU-bound preprocessing serializing on the API-server event loop.

### Cited Findings
- PR #30667 (2025-12-15, closed unmerged): author reports enabling GPU preprocessing in production via `--mm-processor-kwargs '{"device": "cuda"}'` or `"device": "cuda"` in `preprocessor_config.json`, which "significantly reduces CPU overhead in high-concurrency scenarios", but `tensor_data()` in `vllm/v1/utils.py` failed on CUDA tensors (`.numpy()` on cuda) — [vLLM PR #30667](https://github.com/vllm-project/vllm/pull/30667)
- PR #50390 "[EPD] Remove duplicate image preprocessing in EPD and enable preprocess on GPU" (merged 2026-08-05): HF `image_processor` timings per image, CPU vs GPU: 256^2 5.34 vs 0.62 ms (8.6x), 512^2 4.95 vs 0.76 (6.5x), 1024^2 5.85 vs 1.45 (4.0x), 1536^2 8.66 vs 2.63 (3.3x), 2048^2 11.46 vs 4.32 (2.7x), 3072^2 22.61 vs 12.15 (1.9x), 4096^2 40.48 vs 17.88 (2.3x); adds `--mm-processor-device={auto,cpu,cuda}`, where `auto` picks the accelerator only if the instance is an EC producer and not a consumer ("no decoder, no KV cache, so frontend work does not compete with the language model") and `mm_tensor_ipc == torch_shm` ("other transports serialise host bytes, so the result would be copied back and that copy costs more than it saves"); `InputProcessingContext` passes `device="cuda"` to the HF processor ("fast processors accept it; PIL-backed ones drop it"); result: "Change 2 is a latency win, not a throughput win" — it removes "a 50 MB `pixel_values` round trip through host memory" (Qwen3.5-35B-A3B, 2048^2 images) — [vLLM PR #50390](https://github.com/vllm-project/vllm/pull/50390). The local v0.28.0 clone (commit 2cf0a69, 2026-08-24) already contains this logic (`vllm/config/vllm.py`: "EPD encoder instance: keeping the multi-modal processor on CPU because mm_tensor_ipc=%s cannot carry device tensors. Add --mm-tensor-ipc=torch_shm to run it on the accelerator").
- `MultiModalConfig.mm_tensor_ipc`: `"direct_rpc"` (default, msgspec over RPC) or `"torch_shm"` (torch.multiprocessing shared memory, zero-copy); vLLM refuses `torch_shm` unless `VLLM_WORKER_MULTIPROC_METHOD=spawn` ("torch_shm is known to fail without ... spawn") — local clone `vllm/config/multimodal.py`, `vllm/config/vllm.py` ([main](https://github.com/vllm-project/vllm/blob/main/vllm/config/multimodal.py))
- PR #49462 "[Perf] Add mm_tensor_ipc=cuda_ipc TP-aware GPU transport" (open since 2026-07-22): one persistent GPU pool per frontend, IPC handle exported once, per-request D2D copy into a slice, workers open the handle once and copy out (rank 0 D2D, other ranks over NVLink/P2P); "CPU features are rejected ... so this only engages for GPU-preprocessed features"; requires `mm_ipc_gpu_memory_gb > 0`; the author states the existing `torch_shm` transport "is explicitly single-API-server / `tensor_parallel_size == 1` only and routes through a host shared-memory queue"; measured median TTFT (Qwen3.5-35B-A3B, TP=4, 2048^2, c=1): 982.9 ms (cpu/direct_rpc) vs 727.9 (cpu+shm) vs 547.1 (cuda_ipc) — [vLLM PR #49462](https://github.com/vllm-project/vllm/pull/49462)
- Issue #49317 (2026-07-21, closed 2026-08-01): `AsyncLLM.add_request()` called `process_inputs` synchronously on the event-loop thread, serializing per-request HF preprocessing ("GPU is almost idle (`sm ~ 0`)"); resolved via "[Core] Offload raw-prompt preprocessing to renderer thread pool in AsyncLLM" (#49608) and "[Perf] Defer MM embeds loading off the event loop" (#49477) — [vLLM issue #49317](https://github.com/vllm-project/vllm/issues/49317)
- RFC #49288 "Multimodal Asynchronous Collaborative Architecture Sidecar" (open, 2026-07-21): argues preprocessing in the API server "competes for the same event loop, the same GIL, and the same CPU cores", causing "super-linear TTFT inflation under concurrency", and proposes an out-of-process sidecar — [vLLM issue #49288](https://github.com/vllm-project/vllm/issues/49288)
- "EPD (EC connector) Tracker" #52409 (open, 2026-08-15) lists encoder-only ViT CUDA-graph capture in Model Runner V2, EC-connector metrics, `has_pending_push_work` ("prepares for RDMA"), and JSON-array multimodal metadata for the Rust frontend — [vLLM issue #52409](https://github.com/vllm-project/vllm/issues/52409)
- Other 2026 items: "Add Prometheus metrics for the multimodal preprocessing pipeline" (#47860, open 2026-07-07); "Add lossy keyframe-only video loader (pyav_keyframes)" (#45203, 2026-06-10); "[Perf][Frontend] Serialize multimodal render responses directly" (#58660, open 2026-09-25); "[RFC]: Standalone Rust renderer" (#49047, closed 2026-07-18) — [GitHub search](https://github.com/vllm-project/vllm/issues?q=multimodal+preprocessing)
- Issue #24728 "[Performance]: Multi-Modal Benchmark on NVIDIA A100 – Qwen2.5-VL / MiniCPM-V-4 / InternVL3_5" (open since 2025-09-12) reports CPU at 100% with GPU ~20% during video inference and throughput dropping from ~132 tok/s (single image) to ~10 tok/s (30-frame video) — [vLLM issue #24728](https://github.com/vllm-project/vllm/issues/24728) (numbers as summarized by search; see Gaps)

- Academic framing: ModServe (Feb 2025) notes PD-disaggregated systems "overlook the upstream stages of multimodal preprocessing and encoding, which are still tightly coupled within a monolithic serving instance" — [arXiv 2502.00937](https://arxiv.org/abs/2502.00937); "Enabling Disaggregated Multi-Stage MLLM Inference via GPU-Internal Scheduling and Resource Sharing" (2025-12-19) introduces FlashCodec (collaborative multi-GPU video decoding) and UnifiedServe (encoder and LLM "logically decoupled ... yet physically sharing GPU resources"), claiming up to 3.0x more concurrent requests and 4.4x throughput — [arXiv 2512.17574](https://arxiv.org/abs/2512.17574)

### Inferences
- Upstream's own gating rule for GPU preprocessing (only on an encoder-only instance, only with a device-capable transport) is a direct answer to the team's question: in a single-instance, 12-frontend deployment, upstream would currently keep the processor on CPU because the output would be copied back to host anyway (`direct_rpc`) and `torch_shm` is single-API-server.
- The missing piece for the team's layout is a multi-frontend GPU transport; PR #49462 is the closest upstream design (persistent IPC pool per frontend, handle opened once per worker), and SGLang's cuda_ipc pool is a shipped equivalent.

### Gaps

## Key Question 5: GPU log-mel options for audio (torchaudio, NeMo, transformers Whisper/Parakeet) and whether Nemotron's audio front-end is NeMo-derived

### Takeaway
Nemotron-3-Nano-Omni's sound encoder is HF's `ParakeetEncoder` (NeMo FastConformer lineage, Parakeet-TDT-0.6B-v2); its log-mel features are computed outside the model by a `ParakeetFeatureExtractor`-style front-end that already has a torch STFT path with a `device` argument (like Whisper's since April 2024), so moving mel to GPU is a configuration-level change rather than new code; NeMo/Megatron-Core also ship a pure-PyTorch `AudioToMelSpectrogramPreprocessor` with validated parity, and torchaudio's `MelSpectrogram` is a CUDA-capable `nn.Module`. No serving stack surveyed computes audio features on GPU in-model today.

### Cited Findings
- Nemotron 3 Nano Omni pairs a NemotronH MoE backbone with a RADIO v2.5-H vision encoder and a "Parakeet (FastConformer) sound encoder"; audio is resampled to 16 kHz mono and encoded with the Parakeet-TDT-0.6B-v2 FastConformer encoder: log-mel features with a 10 ms hop, three stride-2 conv subsampling layers (~8x), ~12.5 tokens per second — [arXiv 2604.24954 (Nemotron 3 Nano Omni report)](https://arxiv.org/pdf/2604.24954)
- HF repo `audio_model.py`: "This module provides the SoundEncoder (wrapping Parakeet from HuggingFace transformers)"; builds `ParakeetEncoderConfig` (`num_mel_bins` 128, `subsampling_factor` 8, conv kernel 3, stride 2) and `self.encoder = ParakeetEncoder(parakeet_config)`; `forward(input_features: "Mel spectrogram features [batch, seq_len, feature_dim]")` — i.e., mel is an input, not computed in-model — [audio_model.py](https://huggingface.co/nvidia/Nemotron-3-Nano-Omni-30B-A3B-Reasoning-BF16/blob/main/audio_model.py)
- HF repo `processing.py`: audio is loaded with librosa/soundfile (CPU) and the token count "Mirrors `ParakeetFeatureExtractor` (center-padded STFT -> `1 + L // hop` mel frames) followed by `ParakeetEncoder._get_subsampling_output_length`"; default `audio_sampling_rate=16000` — [processing.py](https://huggingface.co/nvidia/Nemotron-3-Nano-Omni-30B-A3B-Reasoning-BF16/blob/main/processing.py)
- transformers `ParakeetFeatureExtractor`: "extracts mel-filter bank features from raw speech using a custom numpy implementation of the Short Time Fourier Transform which should match pytorch's `torch.stft`"; `__call__(..., device: str | None = "cpu")` "uses torch for the STFT computation if available, otherwise a slower NumPy based one"; `_torch_extract_fbank_features(waveform, device)` uses `torch.hann_window(win_length, periodic=False, device=device)`, `torch.stft`, librosa slaney mel filters (`norm="slaney"`, fmax = sr/2) moved `.to(device)`, and `log(mel + guard)` — [feature_extraction_parakeet.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/parakeet/feature_extraction_parakeet.py); `ParakeetEncoder.forward` starts at `self.subsampling(input_features, attention_mask)` (`ParakeetEncoderSubsamplingConv2D`) — [modeling_parakeet.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/parakeet/modeling_parakeet.py)
- Whisper: PR #29900 "[Whisper] Computing features on GPU in batch mode for whisper feature extractor" (merged 2024-04-08) added the `device` argument; the PR reports batch feature extraction dropping from 1.5 s to 0.02 s, ~25% lower whisper-small inference latency, and up to 9x faster training depending on CPU — [transformers PR #29900](https://github.com/huggingface/transformers/pull/29900); the extractor docs say the GPU STFT yields "results similar to cpu computing with 1e-5 tolerance" — [feature_extraction_whisper.py (mirror)](https://github.com/huggingface/transformers/blob/main/src/transformers/models/whisper/feature_extraction_whisper.py)

- torchaudio `transforms.MelSpectrogram` is an `nn.Module` listed with "CPU, CUDA" device support; defaults `n_fft=400`, `n_mels=128`, `mel_scale="htk"` (or `"slaney"`), `norm="slaney"` option, `power=2.0` — [torchaudio docs](https://docs.pytorch.org/audio/stable/generated/torchaudio.transforms.MelSpectrogram.html)

### Inferences
- Because the NeMo-style front-end (dither, pre-emphasis, per-feature normalization) and HF's Parakeet extractor differ in details (HF uses `periodic=False` Hann, librosa slaney filters, log with a guard, no dither/preemph in the snippet seen), the GPU implementation must be chosen to match whichever one vLLM's Nemotron Omni path uses; a torch-STFT-on-CUDA port of the exact HF function (`device="cuda"`) is the lowest-risk path and is what Whisper already does.
- Audio mel cost is small relative to video (a 120 s clip at 16 kHz is 1.9 M samples -> 12 k mel frames x 128 bins = ~6 MB fp32), so the GPU benefit is CPU relief and avoiding numpy->torch copies, not raw speed.

### Gaps

- I did not check vLLM 0.28.0's Nemotron Omni model file to confirm which extractor (HF Parakeet vs. NeMo-derived) it calls, per the division of labor with the vLLM-internals researcher.
- No serving-stack documentation found that computes log-mel on GPU inside the serving process other than the Whisper HF extractor's `device` option; NeMo/Riva deployments compute features on GPU as part of the model graph, but I found no 2025–2026 primary source stating this for an LLM-serving stack.

## Key Question 6: Architectural constraints of GPU preprocessing in 12 API-server processes (CUDA contexts, MPS, memory, cross-process GPU tensors / CUDA IPC)

### Takeaway
Each API server already owns a CUDA context (vLLM measures ~1.8 GiB per API server for context + driver state with PyNvVideoCodec), and under MPS each client has its own address space and can be memory-limited (`CUDA_MPS_PINNED_DEVICE_MEM_LIMIT`) and SM-limited (`CUDA_MPS_ACTIVE_THREAD_PERCENTAGE`); GPU tensors can cross process boundaries only via CUDA IPC (same device, producer keeps the allocation alive, handles cannot be opened in the exporting process, spawn/forkserver required in PyTorch), which is exactly what SGLang's `cuda_ipc` pool, TRT-LLM's `SharedTensorContainer` and vLLM's proposed `cuda_ipc` transport implement with persistent pools to amortize handle open/close.

### Cited Findings
- MPS architecture: "Work launched to the compute engine from work queues belonging to different CUDA contexts cannot execute concurrently" without MPS (time-sliced); under MPS "clients submit work directly to the GPU without passing through the MPS server. Each MPS client owns its own GPU address space instead of sharing GPU address space with all other MPS clients and supports limited execution resource provisioning for Quality of Service (QoS)" — [NVIDIA MPS docs: Architecture](https://docs.nvidia.com/deploy/mps/architecture.html)
- Context creation cost: "Creating a context is a costly operation in terms of time, memory, and the hardware resources ... it is recommended that users create a pool of contexts ... upfront" — [NVIDIA MPS docs: Common Tasks](https://docs.nvidia.com/deploy/mps/common-tasks.html)
- Per-client limits: `CUDA_MPS_PINNED_DEVICE_MEM_LIMIT` "limits the amount of GPU memory that is allocatable by CUDA APIs by the client process" (per-device values, e.g. `0=1G,1=512MB`); `CUDA_MPS_ACTIVE_THREAD_PERCENTAGE` "sets the portion of the available threads that can be used by the client contexts" and `cudaDevAttrMultiProcessorCount` reflects it; "Under MPS, each server's clients share one pool of connections ... Volta MPS clients exclusively owns the connections set aside for the client in the shared pool, so setting [CUDA_DEVICE_MAX_CONNECTIONS] under Volta MPS may reduce the number of available clients. The default value is 2" — [NVIDIA MPS docs: Environment Variables](https://docs.nvidia.com/deploy/mps/appendix-environment-variables.html)
- Client-count limit: Volta and later support 48 MPS clients per GPU (16 for SM 3.5–6.0) — [NVIDIA forum: Question about CUDA MPS](https://forums.developer.nvidia.com/t/question-about-cuda-mps/70217), [MPS docs: When to Use MPS](https://docs.nvidia.com/deploy/mps/latest/when-to-use-mps.html)
- CUDA IPC with MPS: NVIDIA states CUDA IPC "is not supported with MPS on Tegra platforms" (implying support on discrete GPUs) — [MPS docs via search summary](https://docs.nvidia.com/deploy/mps/latest/when-to-use-mps.html) (see Gaps)
- PyTorch CUDA tensor sharing: "Sharing CUDA tensors between processes is supported only in Python 3, using a `spawn` or `forkserver` start methods"; "the sending process is required to keep the original tensor as long as the receiving process retains a copy of the tensor. The refcounting is implemented under the hood"; "If the consumer process dies abnormally to a fatal signal, the shared tensor could be forever kept in memory as long as the sending process is running"; best practice: release memory ASAP in the consumer (`del x`) — [PyTorch multiprocessing docs](https://docs.pytorch.org/docs/stable/multiprocessing.html) ([source md](https://github.com/pytorch/pytorch/blob/main/docs/source/multiprocessing.md))
- "CUDA IPC handles (reduce_tensor / cudaIpc) cannot be opened by the exporting process" / "CUDA IPC handles are invalid same-process" (TRT-LLM keeps a local store for same-process consumers) — [TRT-LLM shared_tensor.py](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/shared_tensor/shared_tensor.py)
- Persistent-pool designs to amortize IPC: SGLang allocates one CUDA feature pool per tokenizer worker on `base_gpu_id`, splits the `SGLANG_MM_FEATURE_CACHE_MB` budget across workers as a hard cap, caches opened pool handles on the consumer, and uses stream-ordered slice release — [SGLang cuda_ipc.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/multimodal/transport/cuda_ipc.py); vLLM PR #49462: "one persistent GPU pool is allocated once and its CUDA IPC handle exported once ... No per-request `cudaIpcGetMemHandle`"; receivers open the handle "once per process"; slices are recycled "once `tensor_parallel_size` distinct consumers have read it"; rank 0 "plain D2D copy, other ranks read over NVLink/P2P" — [vLLM PR #49462](https://github.com/vllm-project/vllm/pull/49462)
- vLLM's frontend GPU admission control: `mm_ipc_gpu_memory_gb` is "carved out of the engine's KV-cache memory" and frontend decode paths "acquire from a blocking byte-counting semaphore" before allocating; the PyNvVideoCodec backend reserves 128 MiB per decoder slot and vLLM budgets 1.8 GiB "Per-API-server CUDA context and driver allocation, measured with PyNvVideoCodec 2.0.4 on H100" — local clone `vllm/config/multimodal.py`, `vllm/multimodal/video.py` ([main](https://github.com/vllm-project/vllm/blob/main/vllm/multimodal/video.py)); the vLLM blog recommends `--mm-ipc-gpu-memory-gb 2` and to "only reserve the least amount which doesn't impact your throughput" — [vLLM blog 2026-09-18](https://vllm.ai/blog/2026-09-18-pynvvideocodec)
- Per-process CUDA context size (PyTorch community data): "about 1.2 GB per process" in one report, "~500MB" in another; "the size of the context depends on the CUDA version, your GPU, the number of kernels in loaded CUDA libs as well as native PyTorch kernels"; PyTorch binaries with CUDA >= 11.7 enable lazy module loading by default (`CUDA_MODULE_LOADING=LAZY`), which "will create a small context at the init time and will lazily load the device kernel code" — [PyTorch forum: Cuda context size per process](https://discuss.pytorch.org/t/cuda-context-size-per-process/79976), [PyTorch forum: Reduce GPU memory blocked by context](https://discuss.pytorch.org/t/reduce-gpu-memory-blocked-by-context/142587), [NVIDIA forum: Per-process GPU memory overhead](https://forums.developer.nvidia.com/t/per-process-gpu-memory-overhead/23721)
- Interference evidence from SGLang: GPU preprocessing in the frontend process "on `cuda:{base_gpu_id}` — the device the scheduler is serving from" is "one more competitor for that device", so SGLang caps GPU-path preprocessing to one worker; a 1440p image produces "~44 MB" of transient fp32 pixel tensors and OOMs when the KV pool leaves ~17–50 MiB free — [SGLang PR #35349](https://github.com/sgl-project/sglang/pull/35349), [SGLang issue #42511](https://github.com/sgl-project/sglang/issues/42511)
- Multiple CUDA contexts on one GPU degrade performance (DALI's stated reason for its in-process Proxy design) — [DALI PyTorch DALI Proxy](https://docs.nvidia.com/deeplearning/dali/user-guide/docs/plugins/pytorch_dali_proxy.html)
- HF video processors moved device placement to after frame sampling specifically to avoid "a high GPU memory spike with long videos" — [transformers PR #38880](https://github.com/huggingface/transformers/pull/38880)

### Inferences
- Memory budget for 12 frontends on one B200 (~180 GB usable): 12 x ~1.8 GiB of context/driver state (~22 GiB) is already committed by the current PyNvVideoCodec setup; GPU preprocessing adds transient working sets of 0.75 GB (uint8) to ~3 GB (fp32) per in-flight 120 s request, so a global cap (vLLM's byte-counting pool is per process; a cross-process cap would need MPS `CUDA_MPS_PINNED_DEVICE_MEM_LIMIT` per client or a shared semaphore) is the first design decision, not an optimization.
- Transporting GPU `pixel_values` from 12 frontends into the engine requires a CUDA-IPC pool per frontend with the engine opening 12 handles once (SGLang's per-tokenizer-worker pool is the shipped precedent; vLLM PR #49462 is the upstream analogue). The alternative—keeping the host copy (`direct_rpc`)—makes GPU preprocessing a latency-only win (vLLM PR #50390 measured exactly that on EPD).
- MPS's time-slicing-vs-concurrency model means preprocessing kernels from 12 client contexts can overlap with the engine's kernels, but they also contend for SMs and HBM bandwidth with the ViT/LLM; `CUDA_MPS_ACTIVE_THREAD_PERCENTAGE` on the frontends is the documented lever to bound that interference.
- Fixed-function NVDEC does not compete for SMs (vLLM PR #56333's argument), whereas resize/normalize kernels do; so "decode on GPU, preprocess on GPU" shifts the cost from CPU to SM time that would otherwise serve prefill, which is the trade the SGLang numbers (9.30 -> 4.02 req/s with 2 GPU workers) warn about.

### Gaps
- The CUDA Programming Guide's "Interprocess Communication" section text and the current MPS docs' explicit statement on CUDA IPC between MPS clients on discrete GPUs could not be extracted (pages returned only navigation); the "not supported on Tegra" statement is from a search summary and should be confirmed against the current MPS document before relying on CUDA IPC under MPS.
- No primary source found on PyTorch `expandable_segments` allocator interaction with CUDA IPC export (`cuMemExportToShareableHandle`); treat as a configuration risk to test.
- The 48-client limit is documented for Volta-era MPS; I found no B200-specific statement of the client limit or per-client context overhead under MPS.
- No measured number for B200 per-process CUDA context size; the 1.8 GiB figure is H100 + PyNvVideoCodec 2.0.4.
