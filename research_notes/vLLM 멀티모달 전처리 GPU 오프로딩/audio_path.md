# vLLM 0.28.0 audio input path for nvidia/Nemotron-3-Nano-Omni-30B-A3B-Reasoning-BF16 (`use_audio_in_video`): every CPU step, and what can move to GPU

Scope and sources. All vLLM references are to the local clone at tag `v0.28.0` (commit `2cf0a69`, dated 2026-08-24) and are linked as GitHub permalinks at that tag; HF model files are from the repo at sha `e5e9932` (lastModified 2026-08-24); transformers references are to tag `v5.5.3` (the minimum vLLM 0.28.0 requires) unless marked "main". PoC numbers are from `REPORT.md` and the raw run log. Everything under "Inferences" is reasoning from code, not a measurement.

Short version: in vLLM 0.28.0 this model does **not** use an HF feature extractor at all. vLLM ships its own processor (`vllm/transformers_utils/processors/nano_nemotron_vl.py`) and its own torch-based `ParakeetExtractor` (`vllm/model_executor/models/parakeet.py`), which already takes a `device=` argument and computes the log-mel with `torch.stft`; the processor simply never passes a device, so everything runs on the API-server CPU. Audio bytes are decoded by PyAV/FFmpeg (AAC decode is CPU-only; NVDEC has no audio codecs), resampled to 16 kHz by libswresample, and the mel features (not the waveform) are shipped to the engine. The audio-specific CPU work is small by construction; the benchmark's 0.2 cpu-s delta is confounded by the fact that the `use_audio_in_video` branch bypasses the multimodal processor cache that the video-only run benefits from.

## KQ1. vLLM loader: which library decodes audio, how `use_audio_in_video` is handled, is the container demuxed twice, what is returned

### Takeaway
With `mm_processor_kwargs={"use_audio_in_video": true}` the chat endpoint fetches the *same* `video_url` a second time through `AudioMediaIO`, base64-decodes it again, tries libsndfile (which cannot open MPEG-TS/MP4), then opens the whole container a second time with PyAV and decodes the AAC track with FFmpeg at its native sample rate, averaging channels to mono. The result is `(float32 1-D numpy waveform, native_sr)`; resampling to 16 kHz happens later in the model's data parser (libswresample via PyAV, CPU).

### Inferences
- The container is demuxed twice per request (once by the video backend / PoC remux, once by `load_audio_pyav`) and the base64 payload is decoded twice; both are CPU-only and avoidable by design changes (KQ5c), not by GPU offload.
- Because `NanoNemotronVLProcessingInfo.get_hf_processor` goes through `init_processor` (no cache) rather than the cached `ctx.get_hf_processor`, a new `NanoNemotronVLProcessor` (and a new `ParakeetExtractor`) is constructed per request; cheap, but it matters for `torch.compile` guard behaviour (KQ4 hypothesis).
- A per-request `mm_processor_kwargs={"device": "cuda"}` would reach `NanoNemotronVLProcessor.__init__` (which has no `device` or `**kwargs` parameter, L764-774) and fail with a `TypeError`; even if accepted, `__call__` never forwards its `**kwargs` (L1020) to `_preprocess_audio`. Not tested.

### Gaps
- The native sample rate / channel count of the HLS AAC track in the PoC segments is unknown (not in the repo), so the exact resampling ratio (48 k or 44.1 k → 16 k) is unverified.

## KQ2. Feature extractor for this model: class, parameters, numpy vs torch, device support, version requirement

### Takeaway
HF side: the model repo's `processing.py` emits raw waveforms (`sound_clips`); the log-mel is computed inside `modeling.py` at forward time with transformers' `ParakeetFeatureExtractor` on CPU and only then moved to the GPU. vLLM side: vLLM's own `ParakeetExtractor` re-implements the same pipeline (preemphasis 0.97, STFT n_fft 512 / hop 160 / win 400 Hann, 128 slaney mel bins, `log(x + 2^-24)`, per-clip mean/variance normalisation, 30 s clips) entirely in torch with a `device` parameter; both transformers' and vLLM's extractors are GPU-capable code that is invoked with the default `device="cpu"`.

### Inferences
- Token count check: 6 s × 16 kHz = 96,000 samples → one clip (< 30 s) → `96000 // 160 = 600` frames → three stride-2 stages (kernel 3) → 300 → 150 → 75 audio tokens. The run log shows 1783 vs 1705 prompt tokens with/without audio (+78 = 75 + `<so_start>` + `<so_end>` + 1 residual, plausibly from the prompt re-tokenisation in `apply()`), so the full 6 s track was extracted in the benchmark — [run_all_2026-09-17.log L464-474](file:///Users/garamchoi/pyler/nvdec-poc/results/run_all_2026-09-17.log).
- Since vLLM's extractor is a torch re-implementation of transformers' `ParakeetFeatureExtractor` (same constants), moving it to the GPU is a call-site change, not an algorithm change; numerical differences between the two implementations (librosa float32 filters vs `mel_filter_bank` float64) already exist today and are accepted by vLLM.

- Which transformers version first added `device` to `WhisperFeatureExtractor` was not verified (only the `main` source was read).
- No numerical comparison between vLLM's extractor on CPU vs GPU (torch.stft on CUDA uses cuFFT; expected ulp-level differences) was made.

## KQ3. vLLM model implementation and in-tree precedents for computing audio features on the GPU

### Takeaway
The engine-side model (`NanoNemotronVLForConditionalGeneration` in `nano_nemotron_vl.py`) consumes already-computed mel features (`input_audio_features` of shape (clips, frames, 128)); the only in-tree models that take raw waveforms and do the STFT/mel on the GPU inside the model are Voxtral (`torch.stft` in `VoxtralEncoderModel.compute_whisper_melspec`) and MiDashengLM (torchaudio ops in `DashengFrontend`). Every other audio model (Whisper, Ultravox, Qwen2-Audio, Qwen2.5/3-Omni, Gemma3n, Qwen3-ASR, Phi-4-MM, GLM-ASR, Kimi-Audio, FunASR, FireRedASR2, Cohere-ASR, MOSS, AudioFlamingo3, Parakeet/Nemotron) computes features in the processor on CPU.

## KQ4. Where the audio-time cost is actually spent, and which parts are GPU-movable

### Takeaway
By construction the audio-only CPU work for a 6 s clip (base64 ×1 extra, TS demux, AAC decode, swresample, a 601-frame STFT and a 128×257 mel matmul) is small; the benchmark's 0.07 → 0.29 cpu-s delta and 28.8 → 7.9 req/s throughput drop are confounded because the `use_audio_in_video` branch bypasses the multimodal processor cache (so the 12-frame video pixel preprocessing re-runs on every request while the video-only run served cache hits), and because each API server runs multimodal preprocessing in a single-worker executor. The inherently-CPU parts are the demux and the AAC decode; resampling and the mel are GPU-movable.

### Inferences
- Order-of-magnitude per 6 s segment, from the operation counts in the code (unmeasured): base64 of a 0.4 MB payload and the TS demux are each ~ms; AAC-LC decode of ~280 frames of 1024 samples is tens of ms at most on one core; swresample 48 k→16 k is a few ms; the mel is a 601×512-point STFT plus a 128×257×601 matmul (~20 MFLOP) — single-digit to low tens of ms single-threaded (`OMP_NUM_THREADS=1`). Summed, the audio-specific CPU is plausibly 30-80 ms, i.e. well under the 0.2 cpu-s delta.
- The remaining delta is most plausibly the *video* pixel preprocessing (12 frames through `_bicubic_resize_and_normalize`) and tokenisation that the uncached branch re-runs per request, plus the larger per-request IPC payload (pixel values re-sent instead of a cache hit). In production with unique segments both paths pay this cost, so the video-only 0.07 cpu-s is itself optimistic for unique content.
- Latency: with 64 simultaneous arrivals and ~8 req/s service, the median request waits ~4 s, and the audio+video minimum latency (1.6-1.9 s) is comparable to the video-only p50 (2.1 s); the p50 jump is therefore mostly queueing behind the throughput ceiling, not intrinsic per-request audio latency. With GPU SM at 17-35 % and 0.29 cpu-s × 7.9 req/s ≈ 2.3 cores on a 64-core quota, neither GPU nor aggregate CPU is saturated; the single-worker `_mm_executor` makes the ceiling ≈ `api_server_count / wall-time-of-apply`, which points at the frontend `apply()` path (CPU work + anything it waits on) as the thing to profile first.
- Hypothesis to test, not a finding: because a new `ParakeetExtractor` is created per request (KQ1 inference), the `@torch.compile(dynamic=True)` helpers may be guard-checking against a fresh `self` each call; `TORCH_LOGS=recompiles` on an API server would confirm or rule out recompilation or a fallback to eager after the recompile limit.
- GPU-movable vs inherently CPU: demux (S2) and AAC decode (S3) stay on CPU; resample (S5) and mel/normalisation (S7) can run on CUDA with existing library code (torchaudio resample, vLLM's own `ParakeetExtractor(device=...)`); S0/S1/S4/S6 are not compute but can be reduced (KQ5c).

### Gaps
- No per-stage measurement exists in the PoC; the attribution above should be checked by (i) rerunning the live rows with `--mm-processor-cache-gb 0` for both video-only and audio+video, (ii) an audio-only request with a WAV data URL, and (iii) enabling `enable_mm_processor_stats` (programmatically) or `vllm bench mm-processor` to read `apply_hf_processor_secs`.
- No reliable modern figure for FFmpeg AAC decode throughput was found; the "tens of ms" estimate is unsourced.

## KQ5. Minimal change options: (a) device via `mm_processor_kwargs`, (b) mel inside the model forward, (c) CPU-only reductions

### Takeaway
(a) vLLM 0.28.0 already has a `--mm-processor-device` / `mm_processor_kwargs["device"]` convention, but its validator rejects an accelerator on any instance that also runs the language model (only EPD encode-only instances may use it), and the output is copied back to host unless `--mm-tensor-ipc torch_shm`; the Nemotron processor also never forwards a device to its extractor. (b) Computing the mel in the model forward is the clean path: ship the 16 kHz waveform (voxtral/midashenglm precedent) and call the existing `ParakeetExtractor(..., device=cuda)` inside `_process_audio_input`; it removes S7 from the API-server CPU and needs no new transport. (c) The largest CPU reductions that need no GPU are structural: decode the audio in the same PyAV pass as the remux, skip the libsndfile probe, and stop re-running the video pixel transform by making the `use_audio_in_video` branch cache-aware.

- (a) "Pass device to the extractor in the frontend": minimal code is one line (`extractor(audios, device=...)` at processors/nano_nemotron_vl.py L1006) plus a constructor/`__call__` parameter to carry the device (`init_processor` passes merged kwargs straight to the constructor, so a per-request `device` would otherwise `TypeError`). Using the official `device` key triggers the validator's `ValueError` on a normal (non-EPD) instance; using a private key (e.g. `audio_device`) sidesteps the validator but inherits exactly the risks it names (12 API-server processes allocating outside the engine's profiled KV budget, kernel contention) and, under the default `direct_rpc`, the features are copied back to host (`_postprocess_output` L249-250). The PoC's API servers already own CUDA contexts for PyNvVideoCodec, so the context-creation cost is already paid; expected saving is only the mel's CPU time (ms-scale per request), so (a) is low value here.
- (b) "Mel inside the model forward on EngineCore" (recommended if the requirement is "no audio feature extraction on API-server CPU"): processor side, `_preprocess_audio` returns the 16 kHz waveforms (optionally pre-split with `split_audio_into_clips`) and `audio_num_clips`, keeping `get_audio_repl`/`audio_token_count` unchanged (token count is a pure function of length); `_get_audio_fields_config` gets `audio_waveforms=MultiModalFieldConfig.batched("audio")` (variable length → list of tensors, as voxtral's `audio_arrays`); add a `NanoNemotronVLAudioWaveformInputs` schema and accept it in `_parse_and_validate_multimodal_inputs`; in the model, construct `self.audio_extractor = ParakeetExtractor(config.sound_config)` next to `ProjectedParakeet` and in `_process_audio_input` call `self.audio_extractor(waveforms, device=target_device)` before the existing encoder code — the extractor's `torch.compile(dynamic=True)` helpers then compile on the worker during the profiling run, which already feeds dummy audio. Transfer size is comparable (96,000 samples → 192 KB as int16/bf16 or 384 KB fp32, versus 601×128 bf16 features ≈ 154 KB). Gotcha: `_postprocess_output` casts floating tensors to the model dtype (bf16, ~8-bit mantissa) and both precedents accept that; to keep the waveform exact, ship int16 PCM (integer tensors are not cast) or override `_call_hf_processor`. The resample could follow the same route (parser `target_sr=None`, `torchaudio.functional.resample` on CUDA in the model), but swresample-vs-torchaudio numerics are unmeasured, so keep S5 on CPU first.
- (c) CPU-only reductions, in order of expected impact: (1) make the `use_audio_in_video` branch cache-aware (or inject `<so_embedding>` before calling `_cached_apply_hf_processor`) so repeated media behaves like the video-only path — relevant for benchmarks and any repeated segments, not for unique live content; (2) decode the audio in the same PyAV pass that already demuxes the TS for the remux (attach it to the video item's metadata and let `apply()` use it), removing S0-S2 duplication; (3) skip the libsndfile probe for container MIME types (`load_base64` receives `media_type`); (4) expose `audio_resample_method="soxr"` in `get_data_parser` (one line; gain unmeasured and likely small); (5) verify `torch.compile` guard behaviour per the KQ4 hypothesis.
- With `--api-server-count 12`, `torch_shm` creates one `mp.Queue` shared by all API servers; the restriction documented in code is DP/TP/PP = 1, which the single-B200 PoC satisfies, but multi-API-server use of the queue was not verified here.

### Gaps
- No measurement of (b)'s effect on throughput; the gain depends on whether the frontend `apply()` wall time (KQ4) is dominated by the audio features (unlikely per KQ4) or by the video transform; if the latter, (b) alone will not restore the 28.8 req/s and the cache/duplication fixes in (c) matter more.
- Whether `--mm-tensor-ipc torch_shm` works with `--api-server-count 12` and with the PyNvVideoCodec frontend decode path in the same processes was not verified.
- Numerical equivalence of the CPU and CUDA mel (cuFFT vs CPU FFT; `torch.compile` on CUDA vs CPU) and of swresample vs torchaudio resampling was not measured.
