# Nemotron-3-Nano-Omni video preprocessing: HF processor, vLLM 0.28.0 wiring, and GPU-offload options

Scope: `nvidia/Nemotron-3-Nano-Omni-30B-A3B-Reasoning-BF16` HF repo files as of 2026-10-07 (`main`), vLLM at tag `v0.28.0` (local clone, commit `2cf0a69`), transformers `v5.5.3` (the minimum pinned by vLLM 0.28.0's `requirements/common.txt`: `transformers >= 5.5.3`). vLLM citations use GitHub blob URLs at tag v0.28.0 with the line numbers observed in the local clone.

Worked example used throughout: one request with a 6 s 640x360 segment sampled to 12 frames (fps 2).

## Key question 1 - What the HF processor does for video (classes, op sequence, shapes, dtypes, `device`)

### Takeaway
The HF `NemotronH_Nano_Omni_Reasoning_V3Processor` routes video frames through the **image** processor (`NemotronH_Nano_Omni_Reasoning_V3ImageProcessor`, a `BaseImageProcessorFast` subclass) with a `_is_video_mode` flag; each frame is converted PIL->numpy uint8->float32 torch on CPU, bicubic+antialias resized to an aspect-preserving ~1024-patch grid (640x360 -> **672x384**, i.e. upscaled), normalized with the CLIP mean/std, and returned as `pixel_values_videos` float32 `(N, 3, 384, 672)`. The `device` kwarg is accepted by the transformers base class but is **never applied** because this processor overrides `_process_image` to keep PIL images; the separate `video_processing.py` class (which does honor `device`) is not wired into the processor at all.

### Inferences
- Worked numbers for a 640x360 frame (both HF and vLLM rules are the same arithmetic): aspect 1.7778; `ph = round(sqrt(1024/1.7778)) = round(24.0) = 24`, `pw = round(sqrt(1820.4)) = round(42.67) = 43`; `pw` is odd so `pw_up = 44`, `24*44 = 1056 > 1024` -> round down -> `(ph, pw) = (24, 42)` -> target **672x384** (W x H), 1008 patches, **252 tokens per frame/tubelet** after 2x2 pixel shuffle. 640x360 is therefore *upscaled* by the preprocessor. 12 frames with T=2 -> 6 tubelets -> **1512 `<image>` context tokens** before EVS pruning.
- Bytes per request (12 frames): input 12 x 360 x 640 x 3 uint8 = **8,294,400 B (8.29 MB)**; HF output `pixel_values_videos` (12,3,384,672) float32 = **37,158,912 B (37.2 MB)**, i.e. 4.48x the raw frames; the HF model then casts it to bf16 on the GPU.
- The HF video path effectively requires PIL frames: `_compute_target_patches_video` reads `img.width`/`img.height` and `_preprocess` does `np.asarray(img)`; a 4-D numpy/torch video would fail at `.width`. Passing `device="cuda"` to this processor is silently ignored (the override never calls `TorchvisionBackend.process_image`, and `_preprocess` builds CPU tensors from numpy), so output stays CPU float32.
- The `video_processing.py` class is legacy/dead for this checkpoint: it is not in `attributes`, its tiling rule (InternVL ratios at 512 px, `max_num_tiles=12`) differs from the video rule actually used, and `modeling.py` does not consume `video_grid_thw`. Its `device` support is therefore irrelevant to option (a).
- The comment at image_processing.py L55-57 ("we need PIL.resize (bicubic) to match vLLM") contradicts the code and the later comment (L117-121) that uses torch antialiased bicubic; the code path is torch `F.interpolate(..., antialias=True)`.

### Gaps
- The team's description "resize to 560x315" cannot be reproduced from either processor: both rules only emit multiples of 16 and give 672x384 for 640x360. 560x315 is exactly 0.875 x (640x360). No vLLM 0.28.0 code path (`resize_video`/`rescale_video_size` exist in `vllm/multimodal/video.py` L121-139 but have no callers in the loader paths grepped) applies such a scale. Recommend logging `pixel_values_flat_video.shape` in the engine to confirm the actual size; the segment's true coded resolution may differ from 640x360.
- `transformers.image_processing_utils_fast` (the module path `image_processing.py` imports `BaseImageProcessorFast` from) is not a file in the v5.5.3 or v5.6.2 source trees (GitHub API 404); the alias lives in `image_processing_backends.py`. Whether an import shim makes that path importable was not verified; this only affects the HF path, which vLLM does not use.

## Key question 2 - How vLLM 0.28.0 wires this model's multimodal processing

### Takeaway
vLLM maps `NemotronH_Nano_Omni_Reasoning_V3` to `nano_nemotron_vl.NemotronH_Nano_VL_V2` and **does not call the HF processor at all**: `NanoNemotronVLProcessingInfo.get_hf_processor` instantiates vLLM's own `NanoNemotronVLProcessor` (`vllm/transformers_utils/processors/nano_nemotron_vl.py`), whose video path is `video_to_pixel_values` -> `_bicubic_resize_and_normalize` (a `torch.compile(dynamic=True)` CPU function: NHWC->NCHW, float32, bicubic antialias resize to 672x384, `(x/255-mean)/std`, cast to `config.dtype`). The output `pixel_values_flat_video` leaves the API-server process as a **bf16 (12,3,384,672) = 18.6 MB** tensor; in the engine the model only moves it to GPU and runs RADIO (patchify is `Im2Patches` inside the ViT on GPU). Passing `device` is blocked three ways: startup validation refuses an accelerator device on an instance that runs the LM, `NanoNemotronVLProcessor.__init__` has no `**kwargs` so `init_processor` would raise `TypeError`, and `_postprocess_output` copies device tensors back to CPU unless `--mm-tensor-ipc torch_shm`.

### Inferences
- What the CPU stage in the vLLM path actually is (per request, 12 frames): zero-copy `torch.from_numpy` of the pinned NHWC uint8 array (8.29 MB) -> `_bicubic_resize_and_normalize` on CPU (permute, fp32 cast = 37.2 MB intermediate, bicubic antialias upscale to 672x384, normalize, cast) -> **bf16** output (12,3,384,672) = **18,579,456 B (18.6 MB)**, because `config.json` `torch_dtype: "bfloat16"` becomes `config.dtype = torch.bfloat16` in transformers 5.x, and `_postprocess_output` casts floating outputs to `model_config.dtype` (bf16 for the BF16 checkpoint) regardless. The msgpack transport then ships 18.6 MB per request to the engine core (2.24x the raw frames), the receiver LRU cache stores it, and the worker pins + H2D-copies it. There is **no patchification on the CPU** in the video path; "cut into 16x16 patches" happens in `Im2Patches` inside RADIO on the GPU (for images in dynamic-res mode the einops patchify `DynamicResolutionImageTiler.stack` also runs model-side).
- `mm_processor_kwargs={"device":"cuda"}` cannot work for this model in 0.28.0: (1) `validate_mm_processor_device` raises at startup on any instance that runs the language model (which is every non-EPD deployment, including the PoC); (2) even with that bypassed, `init_processor` passes `device` into `NanoNemotronVLProcessor.__init__`, which has no `**kwargs`, so it raises `TypeError` (per-request kwargs hit the same path via `_get_prompt_updates`); (3) the processor code never looks at a `device` anyway, and `_postprocess_output` would copy any device tensor back to CPU unless `torch_shm` IPC is used. vLLM instantiates no transformers processor for this model, so `use_fast`/`BaseImageProcessorFast` device plumbing is moot.
- The `torch.compile(dynamic=True)` decorator means the first video in each of the 12 API-server processes pays an Inductor CPU compile (dynamic shapes), and the compiled kernel runs single-process per request; this is consistent with the measured ~0.27 cpu-s/request being dominated by the fp32 bicubic antialias upscale of 12 frames to 672x384.
- With `--video-pruning-rate` unset, vLLM applies no EVS pruning even though `config.json` carries `video_pruning_rate: 0.7` (only the HF `configuration.py` reads that field); `rows/cols` for EVS come from the processed frame shape.

### Gaps
- Whether vLLM's `ModelConfig` ever rewrites `hf_config.dtype` was not fully traced (`_get_and_verify_dtype` in `vllm/config/model.py` L2214-2291 reads it; no write-back was observed in the grepped lines). The bf16-output conclusion does not depend on it because `_postprocess_output` casts to `model_config.dtype` anyway.
- The hasher's handling of `MediaWithBytes.io_config` for video (fps/num_frames) was not traced beyond `get_item_for_hash` including the metadata dict; if two requests sample the same bytes with different `fps`, the metadata differs (`frames_indices`), which should separate the hashes, but this was not tested.

## Key question 3 - Option (c) precedents and what the vision tower expects

### Takeaway
vLLM 0.28.0 has a direct precedent for moving **normalization** into the model forward (`mm_device_do_normalize` + `FusedInputNorm`, used by Qwen2-VL/Qwen2.5-VL), and an official but EPD-only route for running the whole HF transform on the accelerator (`--mm-processor-device` + `--mm-tensor-ipc torch_shm` on an encode-only instance). There is **no precedent** for resizing raw pixels inside a model forward: every `F.interpolate` in `vllm/model_executor/models/*.py` at v0.28.0 interpolates position embeddings or feature maps. RADIO accepts any input whose H and W are multiples of 16 (patch grid up to `cpe_max_size`=2048, pos-embed interpolated), but the video tubelet path needs all frames of a video at one size and the pixel-shuffle needs even patch counts, so the 672x384 rule must still be applied before the ViT.

### Inferences
- A uint8 NHWC passthrough is compatible with the existing plumbing: `_postprocess_output` leaves uint8 alone, `flat_from_sizes("video", video_num_patches)` slices on dim 0 regardless of layout, msgpack zero-copy carries any dtype, the receiver cache stores it, `reduce_data` `torch.cat`s it, and `group_and_batch_mm_kwargs` pins and H2D-copies it. The only hard contract is the model's `TensorSchema` (`("bvf", 3, "h", "w")`), which would need to become `("bvf", "h", "w", 3)` (or a permute before validation), plus the `rows/cols`/`tokens_in_single_frame` computations that currently read the processed tensor's shape.
- RADIO can consume any H, W multiple of 16 up to 2048 (CPE), so the GPU-side resize only needs to reproduce `get_video_target_size_and_feature_size` (already a pure-arithmetic helper used by both the processor and the prompt-replacement code) - it is not necessary to preserve 672x384 for the tower's sake, but it is necessary to keep the token count consistent with the placeholders inserted by the processor, and to keep the even-patch-count rule for pixel shuffle.

### Gaps
- No vLLM 0.28.0 model was found that ships raw (unresized) pixels to the engine and resizes in forward, so there is no in-tree reference implementation to copy; the closest is Qwen2-VL's normalize-only offload.
- The torch `F.interpolate(mode="bicubic", antialias=True)` CPU vs CUDA kernels are separate implementations; whether they are bit-identical was not verified from sources. The HF repo's comments show that the authors consider resize-kernel differences significant for HF/vLLM agreement (image_processing.py L117-121), so an output A/B is needed for any GPU resize.

## Key question 4 - Comparative assessment of options (a), (b), (c): touch points, data sizes, cache interaction, risks

### Takeaway
(a) `device="cuda"` is not viable on vLLM 0.28.0 for this model without forking (startup validation, `TypeError` in the custom processor, host copy-back). (b) Patching `video_to_pixel_values` in `vllm/transformers_utils/processors/nano_nemotron_vl.py` to run the compiled resize/normalize on CUDA inside the API-server process is a small fork patch (the process already holds a CUDA context for NVDEC under MPS), but it adds an 8.3 MB H2D + 18.6 MB D2H per request, runs un-budgeted GPU work in 12 frontend processes, and goes against upstream's explicit policy; keeping the result on the GPU requires `--mm-tensor-ipc torch_shm` (spawn, DP=1). (c) Sending raw uint8 NHWC frames (8.3 MB, 2.24x smaller than today's bf16 payload) and running `_bicubic_resize_and_normalize` on the engine GPU in `_process_video_input` is the option that removes the CPU stage entirely, shrinks IPC/cache/H2D bytes, keeps GPU work inside the engine's profiled budget, and only touches two model-specific files; it is a fork patch today but is structurally similar to the upstream `mm_device_do_normalize` feature and could be proposed as a model-specific opt-in.

### Inferences
- Data sizes per 12-frame 640x360 request: raw frames 8,294,400 B; today's processor output 18,579,456 B bf16 (fp32 intermediate 37,158,912 B on the CPU); HF-path output 37,158,912 B fp32. With option (c), IPC payload, receiver-cache footprint, and worker H2D all drop from 18.6 MB to 8.3 MB, and the per-process processor cache holds ~2.2x more videos for the same `mm_processor_cache_gb`. The GPU-side resize adds a transient 37 MB fp32 intermediate plus the 18.6 MB bf16 result per video inside `embed_multimodal`, small relative to the ViT activations for 12 frames, and it is exercised by the profile run with 128x512x512 dummy frames (100.7 MB uint8 in, 201 MB bf16 out).
- Option (a) is config-only in intent but is a non-starter here: three independent blockers, and the first (startup validation) is deliberate upstream policy. It would only become relevant in an EPD deployment with an encode-only instance, where this model's custom processor would still need `device` plumbing added.
- Option (b) is the smallest fork patch (one function in the processor module: `torch.from_numpy(video).to("cuda")` before the compiled transform, `.cpu()` after), but: it runs in the 12 API-server processes *and* in the engine process during profiling; each process JIT-compiles the CUDA kernels on first use; the GPU memory is not covered by the engine's budget unless the patch also leases bytes from the `mm_ipc_gpu_memory_gb` pool (`get_mm_gpu_ipc_pool().acquire(...)`), which the PoC must already size for NVDEC; it adds PCIe traffic (8.3 MB up, 18.6 MB down) that upstream judged "costs more than it saves" for the general case; and it contends with the engine on the same GPU under MPS. A variant that resizes right after decode, before the pinned D2H in `_decode_to_pinned_host`, would avoid the extra H2D but changes the loader's `np.ndarray` contract that hashing and prompt replacement depend on. Keeping the result on the GPU (`--mm-tensor-ipc torch_shm`) avoids the D2H but requires spawn and is DP=1-only, and its interaction with 12 API-server processes and a GPU-resident receiver cache is untested here.
- Option (c) is the only one that removes the CPU resize/normalize entirely while keeping GPU work inside the engine's profiled budget and reducing bytes moved. Required code (fork patch, 2 files): processor emits `pixel_values_flat_video` as uint8 NHWC `(frames, H, W, 3)` (zero-copy `torch.from_numpy`) and computes `tokens_in_single_frame` from `get_video_target_size_and_feature_size` instead of the processed shape; model changes the schema to `("bvf", "h", "w", 3)`, computes `(tw, th)` from the raw frame shape, calls `_bicubic_resize_and_normalize(frames_uint8_nhwc, size=(th, tw), norm_mean.to(device), norm_std.to(device), dtype=llm_dtype)` per video in `_extract_video_embeddings_temporal` (videos are already processed one at a time because of `requires_sequential_video_encoding`), and derives `rows/cols` for EVS from the resized shape. Prompt replacement, hashing, field configs and dummy data need no change. Upstream path: present it like `mm_device_do_normalize` (model-level `supports_*` flag + config switch) since no in-tree model resizes in forward yet.
- Numerical risk is identical for (b) and (c): the same torch op runs on CUDA instead of CPU; bf16 inputs to the ViT will differ at most in the low bits of the fp32 bicubic/antialias result. An A/B on `pixel_values_flat_video` and on generated text (greedy) against the current CPU path is the required acceptance test, given how sensitive the authors say the stack is to resize-kernel differences.
- Remaining CPU cost per request after (c): NVDEC pinned D2H copy, blake3 hashing of the item (the smaller of ~8.3 MB frames vs the segment bytes, plus metadata), msgpack framing of an 8.3 MB buffer, tokenization/prompt replacement; the ~0.27 cpu-s resize/normalize stage goes to the GPU.

### Gaps
- No measurements of GPU time for the bicubic antialias resize of 12 frames to 672x384 on B200 were found; it must be benchmarked (expected to be sub-millisecond-scale per video, but unverified).
- Whether `torch.compile(dynamic=True)` of `_bicubic_resize_and_normalize` behaves well inside the engine worker (compile latency at the first real video; interaction with `torch.compile`/CUDA-graph settings of the main model, which do not cover `embed_multimodal`) was not verified.
- The exact origin of the "560x315" figure and the per-stage breakdown of the 0.27 cpu-s (compile vs steady-state) are not derivable from the sources read.
