All code citations are to the local clone at tag `v0.28.0` (HEAD `2cf0a69`, "[CI/Build] Pin Cython below 3.3 for arm64 tilelang sdist (#53358)"); GitHub links use the same tag. v0.28.0 was published 2026-08-26 ([GitHub release](https://github.com/vllm-project/vllm/releases/tag/v0.28.0)). ## Key Question 1: Call chain from `VideoMediaIO.load_bytes` through the PyNvVideoCodec backend — what runs where, the exact device→host copy, and what the backend returns

### Takeaway
In v0.28.0 the pynvvideocodec path is `VideoMediaIO.load_bytes` → `VideoBackend.load_bytes(backend="pynvvideocodec")` → `decode_frames_pynvvideocodec` → `_decode_to_pinned_host`, which decodes only the sampled frame indices into VRAM on GPU 0, stacks them with `torch.from_dlpack`, converts to NHWC, then does an explicit async copy into a **pinned CPU `torch.empty(..., pin_memory=True)`** buffer, synchronises the decoder's CUDA stream, and returns **`host_frames.numpy()` — a CPU `np.ndarray`, NHWC, uint8**; the API contract (`VideoLoader.load_bytes -> tuple[npt.NDArray, dict]`) and the downstream parser both require a NumPy array, which is why the copy exists.

- **The device→host copy (exact lines):**
  ```python
  decoded_frames = decoder.get_batch_frames_by_index(frame_idx)          # L833
  ...
  torch_frames = [torch.from_dlpack(frame) for frame in decoded_frames]  # L847
  device_frames = torch.stack(torch_frames)                               # L850
  device_frames = _pynvvc_frames_to_nhwc(device_frames)                   # L856
  ```

- Stated rationale in the backend docstring: "Decoded frames are copied into pinned host memory before the lease is released, so downstream preprocessing continues to receive a CPU `np.ndarray` in NHWC RGB format." — [vllm/multimodal/video.py L1231-1241](https://github.com/vllm-project/vllm/blob/v0.28.0/vllm/multimodal/video.py#L1231-L1241)

### Inferences
- Frames leave the backend as a CPU NumPy uint8 NHWC array in pinned memory; the GPU copy of the frames is freed (`del device_frames`) and the VRAM lease is released before the HF-processor stage starts, so there is no handle to a GPU-resident copy for a later stage to reuse.
- The copy is required by three contracts at once: the `VideoLoader.load_bytes` return type, the parser's `np.ndarray` expectation (Q2), and vLLM's own Nemotron processor calling `torch.from_numpy(video)` (Q5). Changing only the backend would break all three.

### Gaps
- `SimpleDecoder.get_batch_frames_by_index` output dtype/layout is defined in the PyNvVideoCodec 2.0.4 wheel, not in the clone; the code treats it as uint8 and layout-agnostic (NHWC or NCHW). I did not inspect the wheel.

## Key Question 2: The multimodal-processor path (parse → `apply` → `_call_hf_processor`), where it runs, and how `--mm-processor-kwargs` / per-request `mm_processor_kwargs` reach the HF processor (could `{"device":"cuda"}` get through?)

### Takeaway
Processing runs in the **API-server process** on a **single-worker thread pool** per process (`Renderer._mm_executor`). Parsing converts any `torch.Tensor` video to NumPy via `.numpy()` (a CUDA tensor would raise there). `mm_processor_kwargs` reach the HF processor along two routes: `init_processor` (unfiltered `typ(**merged_kwargs)`) and `call_hf_processor` (filtered against `__call__` with `allow_var_kwargs=True`). A startup `{"device":"cuda"}` is **rejected at config validation** on any instance that also runs the language model; a per-request `{"device":"cuda"}` bypasses that validation and reaches `NanoNemotronVLProcessor.__init__`, which has no `device`/`**kwargs` parameter.

## Key Question 3: Does vLLM require/assert CPU tensors for HF-processor outputs? Where would a GPU tensor fail or be silently moved?

### Takeaway
There is no assert, but there is one deliberate silent move: `InputProcessingContext._postprocess_output` calls `tensor.cpu()` on every non-CPU output tensor unless `mm_tensor_ipc == "torch_shm"`; with `torch_shm` the tensors are kept on device and shipped by CUDA-IPC handle. Downstream code (`reduce_data`, `MsgpackEncoder._encode_tensor`, `tensor_data`, the cache size accounting) tolerates device tensors, so with `direct_rpc` (the default) a GPU-side processor would simply pay a D2H copy per request.

### Cited Findings

### Inferences
- Under the PoC's configuration (default `mm_tensor_ipc="direct_rpc"`, 12 API servers), a GPU-side processor output would be copied back to CPU at `_postprocess_output` L249-250, then serialized over ZMQ; the GPU work would not be wasted, but the D2H copy of the processed (already resized) tensor replaces today's D2H copy of raw frames.

## Key Question 4: What GPU-preprocessing support exists in v0.28.0 (config fields, env vars, flags) and what does not

### Takeaway

## Key Question 5: How vLLM obtains the processor for Nemotron-3-Nano-Omni (class names, `trust_remote_code`, `use_fast`, any `device` argument)

### Takeaway
vLLM does **not** use an HF `AutoProcessor` for this model. ## Key Question 6: Upstream PRs for the pynvvideocodec backend — design notes on the host copy and on keeping frames on GPU

### Takeaway
The backend was merged in PR #44465 "Vram semaphore infra" (2026-06-27, brandonpelfrey) as the first slice of RFC #30839; the PR explicitly describes decode→VRAM→pinned-host→release and states that full zero-copy "will allow preprocessing to work on GPU-resident frame tensors" in "a future PR ... One issue must be discussed with the community first." That future PR has not landed; the draft #31925 (DP=TP=1 only) is still open, the GPU-side processor path that did land (#50390) is restricted to EPD encoders, and newer proposals (#49462 `cuda_ipc`, #57924 Nemotron device-normalize, #57752 lazy decode) are open.

### Cited Findings
- RFC #30839 "[RFC]: Enabling Zero-Copy Video with PyNvVideoCodec and IPC" (open): motivation is CPU pressure and the API-server→ring-buffer→GPU copy; proposes (a) PyNvVideoCodec loader decoding "directly to VRAM", (b) "GPU Shared Memory IPC" via `torch.multiprocessing.Queue` carrying CUDA tensors to CoreEngine; benchmark on H100 with `nvidia/cosmos-reason1-7b`, 3 API servers, CUDA MPS: request throughput 3.24 → 3.32 req/s and CPU utilisation ~30% → <5% — [RFC #30839](https://github.com/vllm-project/vllm/issues/30839)
- Draft PR #31925 "[core] [DO NOT REVIEW] Enabling Zero-Copy Video with PyNvVideoCodec and IPC" (open): "A new PyNvVideoCodec-based HW-based VideoLoader implementation which loads directly into VRAM; A multiprocessing Queue, GPU IPC-based mechanism for zero-transfer/zero-copy sending of video frame data to CoreEngine processes; A rate limiting mechanism ..."; "only valid in the context of single GPU DP=TP=1 cases" — [PR #31925](https://github.com/vllm-project/vllm/pull/31925)
- PR #32104 "Add tensor IPC transfer mechanism for multimodal data" (merged 2026-03-21): introduces the `torch_shm` queue path "for sending multimodal content from API Server -> CoreEngine processes via multiprocessing Queues ... ### Inferences
- Upstream's stated direction for "keep frames on GPU" is the torch_shm/cuda_ipc transport plus a device-side processor, and it is deliberately fenced to deployments where the frontend has the GPU to itself (EPD encoder). The maintainers' objection for co-located engines is contention with the forward pass and unprofiled VRAM in the API-server process (validator text, Q2), not a technical impossibility.
- Nobody upstream has proposed GPU *resize* for Nemotron; #57924 keeps bicubic on CPU and only moves normalization. A PoC that resizes on GPU in the frontend would be new territory relative to upstream.

### Gaps
- `gh search commits` returned nothing for `mm_processor_device`; attribution of the flag to PR #50390 is based on the commit list for `vllm/config/multimodal.py` and `processing/context.py` (both touched by `b30291cf0c`, "[EPD] ... enable preprocess on GPU (#50390)") and the PR body, not on a diff review.
- Review-thread discussion on PR #44465 / RFC #30839 about *why* community discussion was needed before GPU-resident preprocessing was not fetched (only PR/issue bodies were read).

## Synthesis: what would have to change in v0.28.0 to run the Nemotron video transform on GPU inside the API server (co-located engine)

### Takeaway
No flag does this today. Minimum code touch points, all identified above with line numbers: the config validator, the backend's return contract, the parser's `.numpy()`, the Nemotron processor's `torch.from_numpy` / CPU mean-std, the VRAM lease scope, and (to avoid a second D2H copy) the transport.

### Inferences
- A frontend-GPU resize for the PoC would need, at minimum, changes (2)+(3)+(4)+(5); without (6) the output tensor (`pixel_values_flat_video`, model dtype, resized) is still copied D2H once per request, replacing today's D2H copy of raw uint8 frames — for `fps=1, num_frames=128` at 1080p the raw-frame copy is ~796 MB (128×1080×1920×3) whereas the processed tensor is smaller when the target resolution is below source resolution, so the copy volume would likely drop rather than rise (sizes are arithmetic from the code paths, not measured).
- The 12-API-server layout means 12 independent CUDA contexts already exist (MPS in use per the PoC); GPU-side transforms would be issued from each process's single `_mm_executor` thread, so per-process GPU work is naturally serialized and the pool semaphore would be the cross-process limiter.

### Gaps
- No measurement exists in the clone or the PRs for GPU bicubic resize cost on B200 for this model; PR #50390's 2–9× figures are for Qwen fast image processors on an EPD encoder, and PR #57924's are for normalization only on an RTX 3070 Ti.
